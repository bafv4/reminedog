### 優先して直したいもの

利用者に起きやすいもの、直さないと被害が残るものから並べた。

1. **U-1** メニューを開いて Ctrl+= ／ Ctrl+- を押すと、egui の拡大率が変わってクリックの位置がずれる（ブラウザでページを拡大しようとして押しやすい。1 行で直る）

4. **S-1** ページの URL をクエリまで含めて settings.json に保存し、TESTING.md はそのファイルを送るよう頼んでいる
5. **B-2** settings.json の BOM や末尾のカンマ一つで、全設定が黙って既定値に戻る（README は手での編集を勧めている）
6. **B-3** クラッシュのキーを Pause などに移すと、ウェイポイントがまったく使えなくなる

## セキュリティ

### S-1 ページの URL をクエリまで含めて settings.json に平文で保存し、TESTING.md はそのファイルを送るよう頼んでいる

- 重要度：中／確度：確認済み／元：1-1、6-5、10-4
- 該当箇所：`render/src/browser.rs:334-338`、`core/src/settings.rs:61-62, 217-218, 235-249, 264-265`、`docs/TESTING.md:207, 373, 375`、`README.md:265`
- 概要：ログにはホスト名しか出さないのに、同じ URL を `<ゲームフォルダ>/reminedog/settings.json` の `browser_url` には、クエリとフラグメントを含めたまま保存する。`settings.rebinds-*.json`・`settings.corrupt-*.json` の写しにも残る
- 理由：`browser_ui` が `view.url.starts_with("http") && view.url != settings.browser_url` で `settings.browser_url = view.url.clone()` とし、1 秒後に保存する（メニューを閉じていても）。
  OAuth の `code`・`#access_token`、パスワード再設定のリンク、限定公開の動画、Google Drive の共有リンク、Discord の署名付き URL などを最後に開いていると、それが残る。
  TESTING.md:207・373 は不具合の報告に settings.json を添えるよう頼み、:375 は「ログにはトークンなどの秘密の情報は書き出していない」と書いている。Prism のインスタンスの書き出しや Mod パックの zip にも入る
- 影響範囲：ブラウザを使い、settings.json（または写し、ゲームフォルダ）を人に渡した利用者
- 改善案：最後の URL を `%LOCALAPPDATA%\reminedog\`（WebView2 の履歴と同じ場所なので露出は増えない）の別のファイルに移す。
  または、保存するときにクエリとフラグメントと `user:pass@` を落とし、長さに上限を付ける（続きを開くのに要る YouTube の `v=` などはホストを決めて残す）。
  最低限、TESTING.md の 207・373・375 行の文言を直す

### S-2 ページの `window.open` が、ユーザーの操作なしでも見ていたページを置き換える

- 重要度：中／確度：確認済み（WebView2 にポップアップブロッカーがないことは仕様の記述による）／元：6-1
- 該当箇所：`hook-win/src/browser/webview.rs:487-500`
- 概要：`NewWindowRequested` が、どの要求でも `SetHandled(true)` して同じビューで `Navigate` する。`IsUserInitiated` を見ていない
- 理由：広告の iframe がタイマーで呼ぶ `window.open(url)` でも、見ていた記事や動画が置き換わる。
  ホストからの `Navigate` になるので、Chrome にあるポップアップの遮断、別のオリジンの iframe がトップを移動させることへの制限、`data:` の URL をトップで開くことの禁止も効かない。
  移った先が `http` なら `browser_url` に保存され、次の起動でも開く。`--autoplay-policy=no-user-gesture-required` なので、移った先の広告の音も鳴りうる
- 影響範囲：広告の多い攻略サイト・動画サイトを開いている全員。メニューを閉じてゲームをしている間にも起きる
- 改善案：`ICoreWebView2NewWindowRequestedEventArgs::IsUserInitiated` が false なら `SetHandled(true)` だけにする（ページには `null` が返る）。
  CDP のクリックはユーザーの操作として扱われるはずなので、`target=_blank` のリンクは今までどおり開く見込み。`setTimeout(() => open(...))` で URL が変わらないテストを足す

### S-3 既定の置き場所 `C:\reminedog` の DLL を、PC のほかのユーザーが差し替えられる

- 重要度：中／確度：確認済み（この PC の `icacls` の出力）／元：13-1
- 該当箇所：`installer/.../InstallerFrame.kt:622`（`DEFAULT_FOLDER`）、`installer/.../Download.kt:131-150`（`place`）、`README.md:52-53, 62`
- 概要：インストーラーは `C:\` の直下にフォルダを作り、ACL は継承のまま。`C:\` の既定の ACL は子に `Authenticated Users:(M)` を継承させるので、置いた DLL を PC にログオンできる誰でも書き換えられる
- 理由：差し替えられた DLL は、次に Minecraft を起動した利用者の権限で `-agentpath:` から読み込まれ、そのまま任意のコードが動く（利用者が管理者なら権限昇格の経路）。
  `place` の `reminedog.dll.download` も同じフォルダに作るので、コピーから移動までの間のすり替えもありうる。手で入れる手順（README）も同じ場所を勧めている
- 影響範囲：家族共用・学校など、複数のアカウントがある PC。1 人で使う PC では実害は小さい
- 改善案：フォルダを新しく作るときに `AclFileAttributeView`（Java 8 にある）で、所有者・SYSTEM・Administrators だけに置き換える。
  既存のフォルダやファイル（「PC にある DLL を使う」で選んだものも）に Users・Authenticated Users・Everyone の書き込みがあれば赤字で警告する。
  `%LOCALAPPDATA%\reminedog` が ASCII で空白を含まないなら、そちらを既定にすることも検討する

### S-4 ダウンロードした DLL の正当性を確かめる手段が、同じ API の応答だけ

- 重要度：中／確度：確認済み／元：13-2
- 該当箇所：`installer/.../Download.kt:56, 89-92, 161-169`、`README.md:87, 314`、`.github/workflows/release.yml`
- 概要：SHA-256 は、同じ GitHub の API の応答にある `digest` と比べているだけ。転送中の破損は分かるが、リポジトリやアカウントの乗っ取り、Actions の侵害ではどの DLL でも通る。`digest` がない応答は、サイズと `MZ` だけで受け入れる
- 理由：`if (release.sha256 != null && release.sha256 != hash) throw ...`。DLL もインストーラーも署名していない。
  README の「サイズ・SHA-256・DLL であることを確かめてから」は、正当性まで確かめているように読める
- 影響範囲：リリースの公開後に、ダウンロードと「最新版に更新」を使う全員
- 改善案：所有者が手元の鍵で署名した `reminedog-<版>.dll.sig` を添え、インストーラーに埋め込んだ公開鍵で `java.security.Signature`（`SHA256withECDSA` など。Java 8 にある）で確かめ、署名がなければ断る。
  すぐできる対策として、`digest` がない応答は断る。README の文言を「転送の破損を確かめる」に合わせる。Authenticode の署名も検討する

### S-5 配る DLL を作るリリースのジョブが、書き換えられる参照でアクションを使い、キャッシュも戻す

- 重要度：中／確度：確認済み／元：14-2
- 該当箇所：`.github/workflows/release.yml:59-63, 101-105, 128`、`.github/workflows/ci.yml:27-31, 58-59, 82-86`（dependabot の設定なし）
- 概要：アクションはどれもタグかブランチで指定し、SHA で固定していない（`dtolnay/rust-toolchain@stable` は可変のブランチ）。リリースの `dll` ジョブは、rust-cache（`~/.cargo/registry` の展開済みのソースと `target/`）と、CI と同じキーの Gradle のキャッシュを戻してからビルドする
- 理由：tj-actions/changed-files（2025 年）のようにタグを書き換えられると、次のリリースの実行でそのまま取り込まれる。`dll` ジョブのトークンは `contents: read` でも、作った成果物は `release` ジョブ（`contents: write`）がそのまま公開する。この DLL は利用者のゲームの JVM で全権限で動く
- 影響範囲：リリースを入れる全員。起きる見込みは低いが、起きたときの被害は大きい
- 改善案：すべての `uses:` をフルの SHA で固定し（`@<sha> # v4.2.2`）、`.github/dependabot.yml` に `github-actions` を足す。リリースのジョブではキャッシュを使わない。
  `actions/attest-build-provenance` で来歴を付ける。インストーラーのビルドに `gradle/actions/wrapper-validation` を足す

### S-6 CI のスモークテストで、Mesa を「最新」・ハッシュなしで取ってきて JVM に読み込ませ、トークンも残している

- 重要度：中／確度：確認済み／元：14-3
- 該当箇所：`.github/workflows/ci.yml:16-19, 161, 173-200`、`ci/smoke/fetch-lwjgl.sh:52-62`
- 概要：`MESA_TAG` の既定は pal1000/mesa-dist-win の最新のリリースで、ハッシュを確かめずに展開し、`opengl32.dll` を `java.exe` の隣に置く。LWJGL の jar も、同じ Maven Central の `.sha1` と比べるだけ。checkout はトークンを `.git/config` に残す（`persist-credentials` の既定）
- 理由：第三者のバイナリが、版を固定しないまま JVM のプロセスで動き、そのジョブの GITHUB_TOKEN（`contents: read`）を読める。非公開のソースを持ち出されうる。新しい Mesa が出るたびに CI の結果が変わる
- 影響範囲：CI だけ（リリースの成果物には入らない）
- 改善案：既定を特定のタグにし、`.7z` の SHA-256 をワークフローに書いて確かめる。LWJGL も版ごとの SHA-256 の表で確かめる。スモークのジョブの checkout に `persist-credentials: false`

### S-7 latest.log の行を、サーバーが送る文字列の改行で偽造できる

- 重要度：低／確度：確認済み（26.3 の jar とログの書式）／元：11-02
- 該当箇所：`core/src/world.rs:161-209`、`core/src/session.rs:52-66`
- 概要：チャットの行は改行がエスケープされるが、26.3 の `handleServerLinks`（`Received invalid link for type {}:{}`）とキックの理由（`Client disconnected with reason: {}`）は、サーバーの文字列を改行ごとログに出す（log4j2 の書式に置き換えがない）
- 理由：悪意のあるサーバーが偽の ServerLinks を送るだけで、`Starting integrated minecraft server version`・`Stopping server`・`Connecting to` の行を偽造できる。
  サーバーの座標を利用者のシングルプレイのファイルに記録させる、記録を失敗させ続ける、任意の名前の `mp-*.json` に切り替える、ができる（`sanitize_file_component` があるので `waypoints/` の外には書けない）
- 影響範囲：悪意のあるサーバーに入った利用者だけ。被害は地点のファイルの汚染と記録の妨害
- 改善案：シングルプレイの開始は、最新の `session.lock` の更新時刻が直前（例：60 秒以内）のときだけ受け付ける。前回の読み込みからずっとゲーム中（カーソルを捕まえている）だったなら、ワールドの切り替えの行は捨てる（本物の切り替えは画面を経由する）。テストに改行を含む例を足す

### S-9 クライアント証明書・画面共有の既定のダイアログを止めていない

### S-10 ページ自身の `window.focus()` に対策がなく、`window.print` の無効化は iframe で回避できる可能性がある

### P-1 設定と地点の保存（FlushFileBuffers 付き）をゲームの描画スレッドで行い、ゲーム中のページの移動でも走る

- 重要度：中／確度：経路は確認済み、止まる時間は推定／元：1-5、2-1、10-3、11-05
- 該当箇所：`hook-win/src/frame.rs:479-482, 497, 519-544`、`core/src/settings.rs:235-249`、`core/src/waypoint.rs:227-254, 337-342`、`core/src/session.rs:228, 244, 253, 262-266`、`render/src/browser.rs:334-338`
- 概要：`Settings::save`（`create_dir_all`・一時ファイル・`sync_all`・`rename`）を、スワップのフックの中で STATE のロックを持ったまま、本物のスワップの前に行う。地点の記録・名前の変更・削除の保存（失敗中は 10 秒ごとの再試行）も同じ
- 理由：メニューを閉じていても、ページの URL が変われば（YouTube の次の動画、`pushState`、BlueMap のカメラの追従、`#slide=n` の自動送り）1 秒後に保存する（72f8845 は遅らせただけ）。保存のたびに info のログも 1 行出る。FlushFileBuffers は SSD で数 ms、HDD やウイルス対策のスキャン中は数十 ms かかりうる
- 影響範囲：ブラウザを表示して遊ぶ利用者、J で記録するとき
- 改善案：保存を専用のスレッドに移す（`Settings`／直列化したバイト列を `mpsc` で送り、最新のものだけ書く。成否は次のフレームで反映）。
  最低限、`browser_url` は新しい文書の `NavigationCompleted` の URL だけを使い（hash・`pushState` は記録しない）、URL だけの変更は非表示・終了・メニューを閉じたときに保存し、ログは debug にする

### P-2 SeedQueue／Atum のような構成では、描画スレッドで saves の全件の走査が繰り返し起きる

- 重要度：中（その構成の利用者にとって）／確度：推定（停止の長さは測っていない）／元：5-1、11-04

### B-1 置き換え先を待っている間に Ctrl+I でメニューを閉じると、「→ 左 Ctrl」のルールが追加される

- 重要度：中／確度：確認済み／元：7-1
- 該当箇所：`render/src/input.rs:374-378, 428-437, 580-583, 595-599`、`render/src/overlay.rs:782-794`、`render/src/rebinds_ui.rs:335, 342-365`
- 概要：「追加」で元のキーを選んだ後、「X → ？」を待っている間にいつもの Ctrl+I でメニューを閉じると、Ctrl が置き換え先として取られ、「X → 左 Ctrl」が settings に足されて保存・有効になる。メニューは閉じているので気づかない
- 理由：`Capture::Input` は修飾キーの押下でもすぐに取り終える（`captured = Input(LCtrl)`）。続く I の押下でメニューが閉じるが、`cancel_capture()` は `capturing` が残っているときだけ働くので、`captured` は残る。
  次のフレームで overlay が `on_captured` を `!input.ui_open` の判定より先に処理し、`target(source, LCtrl)` がルールを足す。HANDOFF:529 で直したのは、欄を畳んで見えなくなる場合だけ。1 フレームの中で「キー → Esc」と押した場合も同じ
- 影響範囲：置き換えを追加する全員。ゲームに戻ると、元のキーで Ctrl が入る（左 Ctrl をダッシュにしている 1.21.11 では走り出す）
- 改善案：`set_ui_open(false)` で、まだ取り出されていない `Captured::Input` を `Cancelled` に置き換える。または overlay で `!input.ui_open` を `on_captured` より前に見て、閉じた後に届いた `Captured::Input` を捨てる。TESTING.md に「置き換え先を待っている間に Ctrl+I で閉じても、何も増えない」を足す

### B-2 settings.json が JSON として読めないと、UI に何も出さずに全設定が既定値に戻る（BOM・末尾のカンマで起きる）

- 重要度：中／確度：確認済み／元：1-2
- 該当箇所：`core/src/settings.rs:194-231`、`hook-win/src/frame.rs:250`、`README.md:190-205`
- 概要：少しでも JSON の書式を外すと、ファイル全体が `settings.corrupt-<時刻>.json` に移され、キー・ズーム・置き換え・ブラウザの位置などがすべて既定値に戻る。知らせるのはログの warn だけで、README・TESTING・UI のどこにも `corrupt` は出てこない
- 理由：serde_json は UTF-8 の BOM を読み飛ばさない。PowerShell 5.1 の `Set-Content -Encoding utf8`・`Out-File`、メモ帳の「UTF-8 (BOM 付き)」で保存すると BOM が付く。
  末尾のカンマ、README:190-196 の断片（`{}` のない `"rebinds_enabled": true, ...`）を貼っただけ、置き換え以外の項目の型の誤り（`"zoom_factor": "4"`）でも同じ。README は「ゲームを終了してから settings.json に書けば使えます」と手での編集を勧めている
- 影響範囲：設定ファイルを手で直す利用者

### B-3 クラッシュのキーを文字・数字・F キー・テンキーの数字以外にすると、F3+C がまったく使えなくなる

- 重要度：中／確度：確認済み（マウスのボタンにしたときにゲームがクラッシュを始めない点は推定）／元：12-2、5-5
- 該当箇所：`hook-win/src/f3c.rs:115-136, 642-645`、`core/src/keybinds.rs:645-656, 679-688`、`hook-win/src/glfw_input.rs:663-679`、`hook-win/src/sdl_input.rs:354-371`、`hook-win/src/waypoints.rs:485-490, 552, 558-560`
- 概要：クラッシュのキーは送らず、押されていないかを確かめるのに使うだけ。それでも F3+C 用の狭い表で引けないと `Failure::Unsupported` になり、J・K・メニューのボタンが毎回失敗する。文言は「F3+C のキー設定（key.keyboard.pause）には対応していない」と生の名前で、どの割り当てが原因かも書かれない
- 理由：`key_codes` の `crash: ... Some(map(&keys.crash)?)` が修飾キー・コピーと同じ `map` を使う。26.3 の利用者は C が「アイテムを捨てる」で、TESTING も長押しでクラッシュしやすいと注意しているので、クラッシュのキーを空いているキーへ移すのは自然な対処。その結果ウェイポイントが全部止まる。
  `key_label` は表にない名前（`key.keyboard.left.shift`、`key.mouse.4`）をそのまま返す（KeysHeld の文言は `input_label` を使っているのに）
- 影響範囲：1.21.9 以降で、クラッシュのキーを動かした人。修飾キー・コピーを Shift やマウスにしている人の文言
- 改善案：クラッシュのキーは `input_by_name` で引き、確かめられない入力（マウスなど）は失敗にせず確かめない。`Failure::Unsupported` にどの割り当て（修飾キー／座標のコピー／クラッシュ）かを持たせ、ラベルは `input_label` を先に試す。「Minecraft のキー設定で、英字・数字・F キー・テンキーの数字にする」と案内を足す。
  あわせて `Failure::NoHooks` の「クリップボードをフックできなかった」は、キーのコールバック・`glfwGetKey`・`SDL_GetWindowID`・`SDL_GetKeyboardState` がないときにも出るので、「座標を取るのに必要なフックが入らなかった（ログの F3+C の行を見る）」にする

### B-6 SDL2 や Mod の SDL3 も「ゲームの SDL3」として繋ぎ、F3+C の準備完了の印を上書きする

- 重要度：中／確度：コードの道筋は確認済み、きっかけ（SDL を読み込む Mod）は推定／元：4-1
- 該当箇所：`hook-win/src/sdl.rs:201-257`（`is_sdl3`、`attach`）、`hook-win/src/loader.rs:124-131`（`on_module`）、`hook-win/src/sdl_input.rs:189-192, 267-269`、`hook-win/src/f3c.rs:327-341`、`hook-win/src/glfw_input.rs:311`
- 概要：SDL3 かどうかを `SDL_Init`・`SDL_CreateWindow`・`SDL_GL_SwapWindow` の export だけで判定していて、この 3 つは SDL2 にもある。`on_module` は GLFW と SDL を排他にしないので、GLFW を繋いだ後でも SDL らしい DLL が読み込まれればフックを入れる。`f3c::set_hooks_ready` はプロセスに 1 つで、GLFW と SDL の両方が自分の結果で上書きする
- 理由：GLFW 版（1.21.x）に SDL2 を使う Mod（コントローラー系など）を入れると、`Sdl::resolve` が失敗してもログを出すだけで `probe` が SDL3 のシグネチャのデトアを入れ（SDL2 の 6 引数の `SDL_CreateWindow` に 4 引数のデトア）、`sdl_input::install` は `Api` が None なので `set_hooks_ready(false)` を呼ぶ。GLFW が入れた true が消え、以後 J・K・メニューのボタンが「この環境では座標を取得できない（クリップボードをフックできなかった）」になる。
  Mod が自分の SDL3 を読み込み、別のスレッドで `SDL_PollEvent` を呼ぶと、GLFW の F3+C の要求やズームの大きさの保留を横取りしうる（推定）。26.x でゲームの SDL3 より先に別の SDL が読み込まれると、ゲームの SDL3 が「a second SDL3 library was loaded and is ignored」で無視される（読み込みの順序は推定）
- 影響範囲：SDL を自分で読み込む Mod を入れている利用者。利用者の今の構成（バニラの 26.3、Fabric＋Sodium・Iris・Lithium の 1.21.11）では起きない
- 改善案：`is_sdl3` に SDL3 にしかない export（`SDL_GetWindowProperties`・`SDL_GetPointerProperty` など）を加える。`Sdl::resolve` が失敗したら `probe` も `install` もせずに戻る。GLFW と SDL は先に繋いだ一方だけにする（かゲームが実際にスワップしたものに決める）。`set_hooks_ready` はスワップを担当するプラットフォームだけが設定する。SDL でも `take_job(Some(window))`、`tall::take_pending` もウィンドウで絞る

- 改善案：既存のファイルのハッシュがリリースと違えば「既存の DLL を vX で置き換えます」と確かめる。起動時に既存の DLL があれば「PC にある DLL を使う」を選んでおく。「最新版に更新」は `latest()` を先に呼び、確認の画面にタグを出す。既存の DLL の VERSIONINFO を読んで、古くなるなら警告する

### U-7 リリースの「同じ版の下書きがあれば止める」確認が効かない／配る DLL をスモークで確かめない

## 既知の制限で、重大さを見直したいもの

- **CI でのインストーラーのテスト**：Linux の Java 21 でしか動かしていない。Windows に固有の部分（`ATOMIC_MOVE`、`tasklist`、読み込まれた DLL の置き換え）と Java 8 での実行は、手元の確認だけに頼っている（元：13）
- **リリースのワークフローは一度も動かしていない**（HANDOFF）。U-7 の 2 つの問題があるので、最初のリリースの前に直すか、試験版の版（`0.0.0-test.1` など）で一度通して確かめたい（元：14）

## 見たが問題なしと判断したもの（要約）

- **ロックとゲームのコード**：GLFW・SDL3 の全ラッパー、F3+C の送信、キーの置き換えで、ゲームのコードを呼ぶ間に router・f3c・tall のロックを持っていない。ロックの順序は `f3c.rs` と `rebind_state.rs` の規約どおり
- **パニック**：`ffi::catch` の外のフック（`get_key_detour` など）にパニックの経路はない（B-18 の NaN を除く）。release は `panic = "unwind"`
- **GL の状態**：`SavedState`・`CurrentGuard` で戻している。blit は本物の関数で行う
- **F3+C**：送るときにクラッシュのキー（C）を偽装しない。`Burst` の Drop で偽装の解除と修飾キーの解放を必ず行う。SDL3 の要求がフレームをまたがない（26.3 の jar で確認）
- **キーの置き換えの状態機械**：押したときに決め、リピートと解放は記録に従う。キーが押されたまま残る新しい経路はない
- **ファイル**：ウェイポイントのファイル名は `waypoints/` の外に出られない。保存は一時ファイルからの置き換え。新しい版のファイルは上書きしない。latest.log と options.txt の読み方はゲームの書き方と一致する
- **ログ**：コマンドライン・`--accessToken`・ページの URL（ホスト名だけ）・クリップボードの中身は出していない
- **ブラウザ**：CDP の JSON は serde_json で組み立てていて正しくエスケープされる。`media_script` に入るのは数値だけ。`media_notice` はページが細工した値でも通知の文言を作れない。取り込みのコピーの範囲は正しい。世代の扱いで古いスレッドは書かない
- **インストーラー**：INI・JSON の読み書きはランチャーの書式を保つ。ダウンロードは HTTPS のみで https から http へのリダイレクトを追わない。Gradle のラッパーは `distributionSha256Sum` で固定
- **CI**：権限は最小（`release` ジョブだけ `contents: write`）。`workflow_dispatch` の入力は `env` を通していて `run:` に直接展開しない。jdk4py は版と SHA-256 で固定。`Cargo.lock` はコミット済みで git の依存はない
