## 中

### M-1 Linux・macOS のスモークが、テスト用のプログラムの終了コードを見ていない

- **確度**：確認済み
- **該当箇所**：`.github/workflows/ci.yml` の `smoke-linux` の「Smoke」（`bash scripts/linux/smoke.sh ... | tee "$RUNNER_TEMP/smoke.txt"`）、`macos` の「Smoke」。比べる相手は `smoke-windows`（`shell: bash`、`|| status=$?`、`[ "$status" -eq 0 ]`）
- **概要**：どちらのジョブにも `shell:` の指定がありません（ワークフローの `defaults.run.shell` もありません）。そのため、既定のシェルは `bash -e {0}` で、pipefail が付きません。
  - パイプの終了コードは `tee` のもの（0）になり、`smoke.sh` が返す java の終了コードは捨てられます。
  - 成否は `SMOKE OK` とマーカーの grep だけで決まります。
- **理由**：テスト用のプログラムは、`run()` の最後で `SMOKE OK frames=N` を出し、その後に `System.exit` します（`Smoke.java`・`SmokeSdl.java`）。次のどちらも成功扱いになります。
  - JVM の終了の処理の中でのクラッシュ（`Agent_OnUnload`、終了時のネイティブのコード。終了コード 134・139、hs_err が残る）
  - 終了時のハング（Linux は `timeout` の 124、macOS は見張りの kill の 143）
- **影響範囲**：CI の `smoke-linux`（3 つの組み合わせ）と `macos`。実際のゲームでは「終了時に落ちる・固まる」という形で出る退行を、CI が通してしまいます。
- **改善案**：両方の「Smoke」に `shell: bash`（`-eo pipefail`）を付け、`smoke-windows` と同じように `status` を見ます。「Show the agent log」で `hs_err_pid*.log` も表示します。

### M-2 Linux：fc-match の面の番号を確かめずに egui に渡しているので、可変フォントが既定の環境ではオーバーレイが止まる

- **確度**：推定。パニックしてオーバーレイが止まるまでの道筋は確認済み。fc-match がこの値を返す環境は推定
- **該当箇所**：`hook-linux/src/fonts.rs`（`fontconfig()` が `%{index}` をそのまま `index` にする）、`render/src/overlay.rs` の `font_definitions`（`FontData { index: font.index, .. }`）、epaint 0.36.2 `text/fonts.rs:990`（`unwrap_or_else(|err| panic!("Error parsing {name:?} TTF/OTF font file: {err}"))`）
- **概要**：fontconfig の `%{index}` は、可変フォントの名前付きインスタンスでは「インスタンスの番号を上位 16 ビットに入れた値」になります。これをそのまま面の番号として渡すと、epaint がフォントを読めずにパニックします。
  - パニックはスワップのフックの `catch` で止まり、`State::Disabled` になります。
  - フォントはプロセスの間持っているので、そのセッションの間オーバーレイは出ません。
  - fc-match が egui の読めない形式（Type1、ビットマップ）を返した場合も、同じ道筋で止まります。
  - `font_metrics::centering_tweak` は読めなければ `None` を返して済みますが、epaint は済みません。
- **影響範囲**：Linux だけ。日本語の既定のフォントが可変フォントの配布物（Fedora の `google-noto-sans-cjk-vf-fonts` など）の環境です。Debian・Ubuntu の静的な ttc では起きません。
- **改善案**：
  - `fonts.rs` で `index & 0xFFFF`（面の番号だけ）にする。
  - `font_definitions` で `skrifa::FontRef::from_index(&font.data, font.index)` が失敗するフォントは、警告を出して外す。どの OS でも、フォントが原因でオーバーレイが止まらないようになります。

### M-3 Linux：一度成功した切り替えでは X のエラーの処理を省くので、描画先が消えた後の切り替えでゲームが終わりうる

- **確度**：推定。コードの道筋は確認済み。描画先が消える場面は、今の Minecraft では見つけていない
- **該当箇所**：`hook-linux/src/glx.rs` の `make_current`（`if switched.contains(&pair) { switch() }`）と `SWITCHED`、`agent/src/frame.rs` の `run_frame`（`FrameError::DrawableChanged` のとき `runtime.teardown()`）と `teardown`（`context.make_current()`、コメントは「Best effort: the DC may be gone」）
- **概要**：`SWITCHED` に入っている（描画先, コンテキスト）の組では、`trap_x_errors` を通さずに `glXMakeContextCurrent` を呼びます。組を忘れるのは `delete_context` のときだけです。
  - 描画先が変わったとき（`DrawableChanged`）、`teardown` は先に**古い描画先**と自前のコンテキストに切り替えます。オーバーレイの GL の資源を消すためです。
  - 古い描画先が破棄されていると GLXBadDrawable になります。このエラーは Xlib の既定の処理（SDL3 では `X11_SafetyNetErrHandler` を経て既定の処理）に届き、`exit` でゲームごと終わります。
  - XID が再利用されて、互換のない描画先になっていた場合も同じです（BadMatch）。
  - Windows では警告で済むところが、Linux ではプロセスの終了になります。HANDOFF の「失敗しうる呼び出しは自前のエラー処理の下で行う」に反します。
- **影響範囲**：Linux（GLX）。同じウィンドウのまま描画先が作り直される場面が前提で、起きにくいです。ただし、起きるとゲームが強制終了します。
- **改善案**：`Os` に「描画先が変わった」ことを伝える口（例：`forget_surface(surface)`）を足し、`DrawableChanged` のときに呼んで、その描画先の組を `SWITCHED` から外します。もっと簡単には、`create_context` のときに `SWITCHED` を空にします（今の Runtime の組だけを覚える）。

### M-4 macOS：最初の見えるスワップがメインスレッド以外だと、オーバーレイがそのセッションの間ずっと出ない

- **確度**：推定。エージェントの側の道筋は確認済み。macOS の Forge・NeoForge の早い読み込み画面が、メインスレッド以外でスワップするかは確かめていない
- **該当箇所**：`hook-macos/src/nsgl.rs` の `create_context`（`if !on_main_thread() { return Err(...) }`）、`agent/src/frame.rs` の `before_swap`（`State::Uninit => match Runtime::create(..) { Err(e) => { log::error!("overlay disabled: {e}"); State::Disabled } }`）
- **概要**：自前のコンテキストを作れなかったときは、`State::Disabled` になって二度と作り直しません。
  - frame.rs のコメントのとおり、Forge・NeoForge は Minecraft の描画のスレッドより前に、読み込み画面のスレッドから同じウィンドウをスワップします。
  - macOS でそのスレッドのスワップが最初に来ると、次の 2 つが起きます。
    - `Err("not on the main thread ...")` で、そのセッションではオーバーレイが出ない。
    - ログに `[ERROR] overlay disabled` が残る。
- **影響範囲**：macOS（試作）で、メインスレッド以外から先にスワップする Mod ローダーを使うとき。バニラ（`-XstartOnFirstThread` のメインスレッドで描く）には関係しません。
- **改善案**：「このスレッドでは作れない」を、作り直してよい失敗として扱います。
  - 例：`Os` に既定で true を返す `can_create_context_here()` を足し、macOS では `pthread_main_np()` を返す。`State::Uninit if !ws.is_visible(window)` と同じ所で `Uninit` のまま待つ。
  - あわせて、`make_current`（`update`）と `delete_context` にもメインスレッドの確認を足す。

### L-2 SDL3（26.x、Windows）：最小化の判定が SDL のフラグになり、最小化の直後の 1 回のスワップで作り直しと DC の漏れが起こりうる

- **確度**：推定（Windows が最小化の状態を変える時点は確かめていない。#4 は起きないとみている）
- **該当箇所**：`agent/src/frame.rs`（`if ws.minimized(window)`）、`agent/src/sdl.rs` の `minimized`（`SDL_GetWindowFlags & WINDOW_MINIMIZED`）、`hook-win/src/windows.rs` の `window_surface`（`GetDC`）
- **概要**：前の版は Win32 の `IsIconic`（OS の今の状態）でした。SDL のフラグは、ゲームの `SDL_PollEvent` でメッセージを処理したときだけ変わります。
  - 最後のポーリングからスワップまでの間に最小化されると、次のことが起きます。
    - `GetDC` が一時的な DC を返し、`DrawableChanged` で作り直しになる（設定の書き出しを待つ）。
    - その DC は解放されない。
  - 2026-09-29 に直した「最小化中の作り直しの繰り返しと GDI の漏れ」（HANDOFF）が、1 回に限って戻ることになります。
- **影響範囲**：Windows の 26.x のウィンドウモードの最小化。起きても、最小化 1 回につき作り直し 1 回と DC 1 個です。
- **改善案**：`Os` に既定で false の `window_minimized(native_window)` を足し、Windows は `IsIconic` にします。`before_swap` では `ws.minimized(window) || os.window_minimized(..)` を見ます。

### L-3 状態の行の「ゲームフォルダ」で、Linux・macOS ではユーザー名が隠れない

- **確度**：確認済み
- **該当箇所**：`agent/src/frame.rs` の `screen_path`（`APPDATA`・`LOCALAPPDATA`・`USERPROFILE` と区切りの `\` だけ）と `StatusLine::new("ゲームフォルダ", screen_path(..))`
- **概要**：配信中に画面に出てもユーザー名が見えないようにする関数です。`agent/` に移って Linux・macOS でも使われるようになりましたが、そこではどの環境変数にも当たらず、パスがそのまま出ます（例：`/home/<名前>/.local/share/PrismLauncher/...`、`/Users/<名前>/Library/Application Support/minecraft`）。状態の行は、`show_status` が有効ならゲーム中も画面に出ます。

### L-4 GLFW の最小化の判定が、Linux（X11）ではスワップのたびに X サーバーとの往復になる

- **確度**：エージェントの側は確認済み。GLFW の X11 の実装は GLFW のソースの知識による
- **該当箇所**：`agent/src/frame.rs`（`ws.minimized(window)`）、`agent/src/glfw.rs` の `minimized`（`glfwGetWindowAttrib(window, GLFW_ICONIFIED)`）
- **概要**：Windows の GLFW では `IsIconic` と同じですが、X11 の GLFW では `XGetWindowProperty(WM_STATE)` の同期の往復になります。「見直し」で GLX の切り替えの往復を毎フレーム 2 回なくした方針と食い違います。GLFW の文書では `glfwGetWindowAttrib` は main thread only で、Forge の早い読み込み画面のスレッドから呼ぶのは決まりの外です。
- **影響範囲**：Linux の GLFW（1.21 まで）、毎フレーム。リモートの X や遅い X サーバーでは、フレームの時間が少し延びます。
- **改善案**：最小化の判定を `Os`（L-2 と同じ口）に移すか、GLFW のアイコン化のコールバックを包んで状態を覚えておきます。

### L-5 `library::identify` がロックを取った後に「フック済みか」を確かめ直さない

- **確度**：確認済み（起きるのはまれ）
- **該当箇所**：`agent/src/library.rs` の `identify`、`agent/src/glfw.rs` の `attach`／`install`、`agent/src/sdl.rs` の `attach`
- **概要**：同じ GLFW（SDL3）で、最初の関数の引き当てが 2 つのスレッドで同時に起きた場合です。
  - 後のスレッドは、ロックの中で `passed.contains` しか見ずに `attach` に進みます。そのため、同じパスで「a second GLFW (SDL3) library is ignored」という誤った警告をログに出します。フックの働きは正しいままです。
  - また、`MODULE.store` が `*_input::install` より前です。そのため、ロックの外の速い確認を通ったスレッドが、入力の準備が終わる前にフックを受け取れます。
- **影響範囲**：全 OS、まれ。困るのは主に、実機のログを読むときに「ゲームのライブラリが無視された」と読み違えることです。
- **改善案**：ロックを取った直後に `glfw::is_hooked(library) || sdl::is_hooked(library)` を確かめ直します。`MODULE.store` は `*_input::install` の後に移します。

### L-6 ズームの JNI のネイティブが 2 回目に結び付くと、差し替えずに素通しになる（1.13 の LWJGL 3.1.6 には同じ名前のネイティブが 2 つのクラスにある）

- **確度**：3.1.6 の jar と DLL の中身は確認済み。2 回目に結び付く場面は推定
- **該当箇所**：`agent/src/tall.rs` の `wrap_native` の `keep`（`if slot.set(f).is_err() { log::warn!("zoom: another native of {name} is bound; it is left alone"); return false; }`。コメントは「one class has each of these natives (LWJGL 3.2 to 3.4)」）
- **概要**：
  - LWJGL 3.1.6（Minecraft 1.13〜1.13.2）では、次のネイティブが 2 つのクラスにあります。`lwjgl_opengl.dll` の export も別々です。
    - `glBindFramebuffer(II)V`：`GL30` と `ARBFramebufferObject`
    - `glBlitNamedFramebuffer`：`GL45` と `ARBDirectStateAccess`
  - 先に呼ばれて結び付いた方だけを包み、後の方は素通しにします。
  - 1.13 のゲームと Mod が両方のクラスを使うと、後の方の `glBindFramebuffer(…, 0)` は縦長のフレームバッファに差し替わりません。ズームの絵が崩れ、1 秒ほどで引き伸ばすズームに落ちます。
  - 同じメソッドが 2 回結び付く場合（2 つのスレッドが同時に初めて呼ぶ）も、同じ道筋で外れます。
  - 3.1.6 でも、関数を引くネイティブは `WinBase.nGetProcAddress(JJ)J`、`DynamicLinkLoader.ndlsym(JJ)J` で、今の差し替えに当たります。`JavaCritical_` の入口もありません（`lwjgl_opengl.dll` で 0 個）。オーバーレイと、ふつうのズームは 1.13 でも動く見込みです。
- **影響範囲**：1.13 で、両方のクラスを使う構成のときの高精細のズームだけ。3.2 以降は 1 つのクラスなので関係ありません。
- **改善案**：`keep` を、名前とシグネチャごとに複数の本物を覚える形にします（スロットを `(address → 本物)` の小さな表にし、包む関数を本物ごとに用意する。または、包む関数が JNI の `jclass` 引数でクラスを見分ける）。同じアドレスがもう一度来たら、警告を出さずに包む関数を返します。あわせて、`keep` のコメントと README の「1.13 以降」の範囲を、1.13 で確かめるまで「高精細のズームは 1.14 以降で確認」と書きます。

### L-7 Linux（と macOS）では、別の場所のエージェントが 2 つ読み込まれても両方動く

- **確度**：確認済み（macOS の分は HANDOFF の「まだ」にある既知のこと）
- **該当箇所**：`agent/src/os.rs` の `another_copy_runs`（既定で false）、`agent/src/start.rs`、`hook-linux/src/linux.rs`（上書きなし）
- **概要**：Windows は名前付きの mutex で 2 つ目のコピーを止めます。Linux では、別のフォルダの `libreminedog_linux.so` 2 つ（ランチャーの JVM 引数と `JAVA_TOOL_OPTIONS` など）が両方動きます。
  - HotSpot は NativeMethodBind を環境の順に連鎖させるので、フックが二重に重なります。
  - 結果として次のことが起きます。
    - オーバーレイが 2 回描かれる。
    - ホットキーを両方が横取りする。
    - F3+C が二重に送られる。
    - 後の方が `reminedog.log` を回してしまう。
- **影響範囲**：Linux（と macOS）、利用者の設定の誤りのときだけ。
- **改善案**：プロセスの中で 1 つに決まる印を使います（`Agent_OnLoad` の中で、pid を入れた環境変数を `setenv` で立てて確かめる。または `dl_iterate_phdr` で、自分以外に `Agent_OnLoad` を export する reminedog を探す）。

### L-8 Linux：fc-match が日本語のないフォントを返しても、そのまま使う

- **確度**：推定（fc-match は合うものがなくても最も近いものを返す、という fontconfig の挙動による）
- **該当箇所**：`hook-linux/src/fonts.rs` の `read`・`fontconfig`
- **概要**：日本語のフォントがない環境でも、fc-match は DejaVu Sans などを返します。読めた時点で採るので、次のようになります。
  - 候補の場所（Noto Sans CJK、IPA ゴシック）は試されない。
  - 「no Japanese font found」の警告も出ない。
  - 日本語は豆腐になるのに、ログには正常に見える `fonts: .../DejaVuSans.ttf` が出る。
- **影響範囲**：Linux で、fontconfig が CJK のフォントを知らない環境。
- **改善案**：書式に `%{lang}` を足し、`ja` を含むときだけ採ります（または `fc-list :lang=ja file index`）。

### L-9 macOS：日本語フォントの第 2 候補が簡体字中国語のフォント

- **確度**：確認済み（フォントの中身ではなく、名前と用途から判断）
- **該当箇所**：`hook-macos/src/fonts.rs` の `CANDIDATES`（`/System/Library/Fonts/Hiragino Sans GB.ttc`）
- **概要**：ヒラギノ角ゴシック W3 が読めなかったとき、漢字が中国の字形で出ます。W3 はどの macOS にもあるので、ほとんど起きません。
- **改善案**：日本語のヒラギノ（`ヒラギノ丸ゴ ProN W4.ttc` など）を第 2 候補にし、GB は外すか後ろに回します。

### L-10 ビルドのスクリプトが、Cargo の出力先の設定を見ていない

- **確度**：確認済み（起きるのは、利用者が出力先を変えているときだけ）
- **該当箇所**：`scripts/windows/build.ps1`（`target\release\reminedog.dll` に決め打ち）、`scripts/linux/build.sh`・`scripts/macos/build.sh`（`${CARGO_TARGET_DIR:-$repo/target}`）
- **概要**：
  - `build.ps1` は `CARGO_TARGET_DIR` を見ません。
  - `build.sh` は `~/.cargo/config.toml` の `build.target-dir` を見ません。
  - どちらも、出力先が変えられていると、リポジトリの `target` に残っている古い DLL・.so を確かめて `dist`（`-InstallDir`）にコピーしてしまいます。残っていなければ、分かりにくいエラーで止まります。
  - `build.sh` の `--out` の相対パスは、`cd "$repo"` の後に使うので、リポジトリを起点に解釈されます。
- **影響範囲**：手元のビルドだけ（CI、リリース、`scripts/linux/run.sh` の中は正しい）。
- **改善案**：出力先を `cargo metadata --format-version 1 --no-deps` の `target_directory` から取ります。`--out` は `cd` の前に絶対パスにします。

### L-11 Docker の中のスモークでは、ログとスクリーンショットがコンテナと一緒に消える

- **確度**：確認済み
- **該当箇所**：`scripts/linux/run.sh`（`docker run --rm`。マウントは `/src`、registry、`/target`）、`scripts/linux/smoke.sh`（`SMOKE_RUN` の既定は `/tmp/smoke-run`）、README の「動かして確かめる」の「ログは `/tmp/smoke-run/reminedog/reminedog.log` です」
- **概要**：README のとおり `scripts/linux/run.sh scripts/linux/smoke.sh ...` を実行すると、エージェントのログと `smoke-screenshot.png` はコンテナの一時的なファイルシステムに書かれ、`--rm` で消えます。`smoke.sh` が最後に出すのはテスト用のプログラムの出力だけです。
- **影響範囲**：Windows から Docker で Linux のスモークを動かす手順。CI は `SMOKE_RUN` を変えているので関係ありません。
- **改善案**：`SMOKE_RUN` の既定を、ボリュームの上の `/target/smoke-run` にします（`SMOKE_CACHE` と同じ考え方）。または、`smoke.sh` の最後でエージェントのログも出します。README も合わせます。

### L-12 macOS の smoke.sh：時間切れの表示が捨てられ、SIGTERM で止まらない JVM は待ち続ける

- **確度**：表示の件は確認済み。SIGKILL がない件は推定
- **該当箇所**：`scripts/macos/smoke.sh`（`(sleep ... && kill "$java" && echo "smoke.sh: timed out" >&2) >/dev/null 2>&1 &`）
- **概要**：
  - 見張りのサブシェル全体の標準エラーを /dev/null に向けているので、「timed out」も出ません。時間切れか、シグナルで落ちたのかを区別できません（`exit 143` だけが出ます）。
  - 送るのは SIGTERM だけなので、JVM が終われなければ、ジョブの `timeout-minutes` まで `wait` が戻りません。
- **改善案**：見張りが kill したら印のファイルを作り、`wait` の後で表示します（または `exec 3>&2` で元の標準エラーを残す）。数秒待って生きていれば `kill -9` します。

### L-13 macOS の smoke.sh：Intel の Mac では jar のハッシュがなく、必ず失敗する

- **確度**：確認済み
- **該当箇所**：`scripts/macos/smoke.sh`（`arm64` 以外は `natives=natives-macos`）、`ci/smoke/lwjgl.sha256`（`natives-macos-arm64` だけ）
- **概要**：`fetch-lwjgl.sh` は、ハッシュのない jar を拒否して終わります（安全な側に止まるので、確認の抜け道ではありません）。
- **改善案**：`natives-macos` の jar（3.3.3、3.4.3。sdl を含む）のハッシュを足します。または、x86_64 では「Apple silicon だけ」と出して止めます。README にも書きます。

### L-14 `scripts/linux/run.sh` がコンテナを root で動かすので、WSL や Linux のファイルシステムのリポジトリには root のファイルが残る

- **確度**：推定
- **該当箇所**：`scripts/linux/run.sh`（`docker run` に `--user` がない）
- **概要**：`build.sh` の `dist/linux` や、`--installer` の `installer/build` などが root の持ち物として作られます。Windows のドライブでは問題になりませんが、WSL のファイルシステムに置いたリポジトリでは、後で消したり上書きしたりできなくなります。
- **改善案**：`--user "$(id -u):$(id -g)"` にし、`HOME` を書ける場所に向けます。または、最後に `chown` で戻します。

## 既知のことで、重大さを見直したいもの

- **リリースが、試作の macOS のジョブに止められうる**（#9）
  - リリースの check のジョブは「そのコミットの CI の全体が成功」を条件にしています。
  - そのため、試作の `macos` のジョブが不安定だと、Windows のリリースも止まります。
  - 必要なら、リリースの条件を Windows・インストーラー・Linux のジョブに絞ります。
- **hook-macos の x86_64 の分岐は、CI の clippy を通っていない**（#9）
  - 対象は `objc_msgSend_stret` など。CI の macOS のジョブは Apple silicon の clippy だけで、x86_64 はビルドだけです（警告ではジョブは落ちません）。
  - 手元では、Windows から `--target x86_64-apple-darwin` で clippy を通しています。

## 見たが問題なしと判断したもの

- **JVMTI**（#1）：
  - 関数表の番号、`jvmtiEventCallbacks` の並びと大きさ、capability のビット 30、フェーズの確認は合っています。
  - 差し替えるシグネチャ（`(JJ)J`／`(JJJ)J`、`ndlsym`）も合っています。LWJGL 3.1.6 でも同じでした。
  - `Original` の Release・Acquire の順序、`start` の順序（`os::set` が jvmti より前）、`build.rs` の版の受け渡しにも問題はありません。
- **ズーム**（#2）：
  - JNI のネイティブの型と引数の数は合っています。
  - `Swapping` は、自前のフレームバッファが結び付いていて、ゲームのコンテキストのときだけ挟みます。
  - ズームの開始・終了、最小化での `release()`、`real_warp_y`（SDL3 のマウスの移動）、包む関数の中にパニックの道がないことも確かめました。
- **GLFW・SDL3**（#3・#4）：
  - フックの表の名前と型は合っています。
  - コールバックの差し替え（null で外す・入れ直す）にも問題はありません。
  - ロックの順序（INJECTED → f3c だけが入れ子）と、ゲームのコードを呼ぶ間にロックを持たないことは、前の版から変わっていません。
  - GLFW と SDL3 は先に取り付けた一方だけになり、前回の B-6（`set_hooks_ready` を上書きし合う）は解消しています。
- **フレームと GL**（#5）：
  - `OwnContext` と `CurrentGuard` は、失敗したときと Drop のときに元に戻します。削除は自前のコンテキストが今でないときだけです。
  - `GET_INTEGERV` のキャッシュは、ゲームのコンテキスト（同じピクセルフォーマット）の上でだけ使っています。
  - ロックの順序（STATE → waypoints → router）にも問題はありません。
- **Windows の Os**（#6）：指摘はありません。
  - `GetProcAddress` は `jvmti` の差し替え（Java のスレッド）からだけ呼ばれ、ローダーロックの中から呼ばれる道はありません。
  - `keys.rs` は、前の `rebind_state.rs` から同じ中身のまま移っています。
  - `another_copy_runs`・`return_addresses` の移動、WGL の関数の型、CS_OWNDC の前提、ブラウザのタイトルの切り詰め（egui 0.36.2 の `title_ui` と照らし合わせた）も確かめました。ログにコマンドラインや URL は出ていません。
- **Linux**（#7）：
  - GLX・Xlib の関数の型、`XErrorEvent` の並び、`dlinfo` の `link_map` の読み方、`RTLD_NOLOAD` の参照は合っています。
  - `trap_x_errors` と `SWITCHED` のロックの順序にも問題はありません。
- **macOS**（#8）：
  - `objc_msgSend` の呼び方は、x86_64 と arm64 のどちらでも合っています（`NSRect` の stret と HFA、BOOL、NSInteger・NSUInteger、CGFloat）。
  - autorelease pool の範囲と retain／release の対応、切り替えの前の `glFlush` と `update`、`OWN` のロックにも問題はありません。
- **CI とスクリプト**（#9）：
  - CI のマーカーの文字列は、すべてログの実際の文言と一致しています。
  - `fetch-lwjgl.sh` は、`sha256sum`・`shasum` のどちらでも安全な側に倒れます。
  - `.gitattributes`（シェルスクリプトと `gradlew` は LF）、アクションの SHA の固定、`--locked`、ライブラリの名前の衝突がないこと、`build.ps1` の終了コードと jar の名前も確かめました。

確かめていないこと：実機と実行時の動き。どの単位もコードを読んで調べただけで、ビルド・テスト・スモークは走らせていません。集約役が確かめたのは、コードの読み直しと LWJGL 3.1.6 の jar・DLL の中身だけです。
