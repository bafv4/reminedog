# サバイバル向けゲーム内ツール（仮称）— 設計の引き継ぎ

## 目的

Toolscreen（https://github.com/jojoe77777/Toolscreen 、MCSR向け・C++・MIT）のサバイバル版に当たるものを作る。
Modではなくゲーム外のネイティブライブラリとして動かし、**Minecraftのバージョンに依存しない**ことを重視する。

### 欲しい機能（初期スコープ）
1. **座標の記録**：ホットキーで現在地を名前付きで保存する。**ワールド／サーバーごと**に管理する
2. **ズーム**：画面の中央付近を拡大表示する
3. **ゲーム内UI**：ウェイポイントの名前入力、一覧表示、選択

## 決定事項

- **方式**：Rust製のネイティブエージェント（検討した案の中の「②」）。Toolscreenのフォークや外部オーバーレイ方式は採用しない
- **言語**：Rust
- **検証環境**：まずWindows 10/11 x64（手元で検証できる）。将来はFedora（Linux）にも対応したい
- **対応バージョン**：Minecraft 1.13以降（LWJGL3 / GLFW を使うバージョン。F3+Cでの座標コピーも1.13から）。1.12以前は対象外

### 採用しなかった案（理由）
- Toolscreenのフォーク：ズームとImGuiのUIが既にあって早いが、コードがC++で規模が大きく、MCSR向けの前提が多く、Windows専用
- 外部オーバーレイ（Tauri＋透明ウィンドウ）：開発は楽だが、排他的フルスクリーンでは重ねられない
- Java Agent（`-javaagent`）／Fabric Mod：ゲーム内部のデータに触れるが、バージョン依存が強い

## アーキテクチャ

### 読み込み
- JVMの引数に `-agentpath:C:\path\to\xxx.dll` を追加する（Prism LauncherならインスタンスのJVM引数の欄）
- JVMTIの `Agent_OnLoad` が入口。外部からの注入用exeは使わない（ウイルス対策の誤検知も避けられる）
- `-agentpath:` はLinuxでも同じように使える

### フック（インラインのデトア。`retour` か `minhook` クレート）
IATフックではなくインラインのデトアにする。LWJGLは関数のアドレスを取得して保持し、そこから直接呼び出すと考えられるため（要検証）。

1. `Agent_OnLoad` で `LoadLibraryExW`（と `LoadLibraryW`）をフックする
2. `glfw.dll` が読み込まれた瞬間に、以下のGLFW関数をデトアする
3. `opengl32.dll` の `wglSwapBuffers` をデトアする

| フック対象 | 用途 |
|---|---|
| `wglSwapBuffers` | フレームの最後でズームとUIを描く |
| `glfwSetKeyCallback` / `glfwSetCharCallback` | Minecraftのコールバックを包む。ホットキーの横取り、UI表示中の入力遮断、キー入力の偽装 |
| `glfwSetMouseButtonCallback` / `glfwSetCursorPosCallback` / `glfwSetScrollCallback` | UI表示中はeguiに渡し、ゲームには渡さない（視点が回るのを防ぐ） |
| `glfwGetKey` | F3+Cの偽装時に「F3が押されている」と返す |
| `glfwSetClipboardString` | F3+Cの出力を横取りする（OSのクリップボードには渡さない） |
| `glfwSetInputMode` など | UIを開いている間はカーソルを表示し、閉じたら元に戻す |

### 座標の取得（F3+C）
1. ホットキーを押す
2. 保持しておいたMinecraftのキーコールバックを直接呼び、Cキーを押したことにする。その間は `glfwGetKey(F3)` にPRESSを返す
3. Minecraftが呼ぶ `glfwSetClipboardString` を横取りし、`/execute in minecraft:overworld run tp @s x y z yaw pitch` 形式の文字列を正規表現でパースする（ディメンションも取れる）
4. OSのクリップボードは汚れないので、退避や復元は不要
- 偽装したキー入力はメインスレッド（swapのフックの中など）で送る。GLFWのコールバックは通常メインスレッドで呼ばれるため

### ワールドの判定
- シングルプレイ：`saves/<ワールド>/session.lock` が更新・ロックされているワールドを今のワールドとみなす
- マルチプレイ：`logs/latest.log` の接続先ホストが書かれた行を監視する
- 保存先の案：インスタンスフォルダの `waypoints/<ワールド or サーバー>.json`

### 描画
- **同じHDCに自分専用のGLコンテキストを作り**、swapのフックの中でだけ切り替える
  ```
  game_ctx = wglGetCurrentContext()
  wglMakeCurrent(hdc, my_ctx)
  ズーム・UIを描く
  wglMakeCurrent(hdc, game_ctx)
  本物の wglSwapBuffers を呼ぶ
  ```
  → Minecraftの描画状態を壊さない。ゲームがCore ProfileかCompatibility Profileか（1.17の前後）にも左右されない
- **ズーム**：デフォルトのフレームバッファの中央部分を `glBlitFramebuffer` で画面全体に引き伸ばす
  - 将来：一時的に高い解像度で描画してから切り出す方式（遠くの景色を細かく見られる）
- **UI**：egui + egui_glow

### 日本語
- フォント：Noto Sans JPを埋め込むか、OSのフォント（游ゴシックなど）を読み込む
- IME：確定した文字はcharコールバック経由で届く。GLFWは変換中の文字を渡さないので、変換中の表示は当面あきらめる。将来 `WM_IME_COMPOSITION` などをフックして改善する

## 既知の制約
- 座標はF3+Cを送ったときにしか取れない。現在地を常時HUDに出すのは難しい（バージョンによってはF3+Cのたびにチャットにメッセージが出る）
  → 初期は「記録」「一覧」「ホットキーを押したときに距離と方角を表示」の範囲にとどめる
- サーバーによってはクライアント改変ツールが規約違反になりうる

- [ ] LWJGLが関数のアドレスを保持して直接呼んでいるか（インラインのデトアで確実に捕まえられるか）
- [ ] MinecraftのF3+Cの判定が `glfwGetKey` でF3の状態を見ているか

## プロトタイプの手順
1. `-agentpath:` で読み込み、`wglSwapBuffers` をフックし、自分のコンテキストでeguiのウィンドウを1つ描く
2. ホットキーでそのウィンドウを開閉し、開いている間はマウスとキーボードの入力をeguiが受け取る（ゲームには渡さない）
3. F3+Cを偽装して横取りし、パースした座標をeguiのウィンドウに表示する

## 追記：実装前のレビュー（2026-09-29）

資料を読んだうえで、実装に反映する点をまとめる。「確度が高い」ものは設計を変更し、「要確認」はプロトタイプで確かめる。

### 設計の変更（確度が高いもの）

1. **ズームは2段階で行う**
   読み込み元と書き込み先が同じデフォルトのフレームバッファで矩形が重なると、`glBlitFramebuffer` の結果はGLの仕様で未定義になる。
   中央部分をいったん自前のFBOに同じ大きさでコピーし、そのFBOから画面全体に引き伸ばす。
   ドライバの設定でデフォルトのフレームバッファにMSAAが強制されていても、同じ大きさのコピーなら解決（resolve）できる。
2. **コールバックを登録する関数のフックは、Minecraft側のポインタを返す**
   `glfwSetKeyCallback` などの戻り値（前のコールバック）には、自前のラッパーではなくMinecraftが登録したポインタを返す。
   LWJGLは終了時に `Callbacks.glfwFreeCallbacks` で戻り値のポインタを解放するため、ラッパーを返すと終了時にクラッシュするおそれがある。
3. **DLLの読み込みは `LdrRegisterDllNotification` で検知する**
   `kernel32` の `LoadLibraryExW` をフックすると、`LoadLibraryA` から kernelbase の内部を通る経路を取りこぼすおそれがある。
   `LdrRegisterDllNotification`（MSDNに載っている通知用のAPI）なら、デトアなしですべてのDLLの読み込みを拾える。
   - 通知はDLLがマップされた直後、`LoadLibrary` が戻る前に届く。LWJGLがGLFWの関数を呼ぶ前にフックを入れられる
   - `Agent_OnLoad` の時点では `opengl32.dll` も読み込まれていない
   - GLFWかどうかは、ファイル名ではなく `glfwInit` などをエクスポートしているかで判定する（Prismのシステムの GLFW、名前の違うDLLにも対応できる）
4. **LWJGLは関数のアドレスを保持して直接呼ぶ（ほぼ確定）**
   LWJGLは `GetProcAddress` で得たアドレスを `GLFW.Functions` の static final のフィールドに持つ。IATのフックでは捕まらず、インラインのデトアが必要という前提は正しい。
5. **swapのフックは `glfwSwapBuffers` にする**
   GLFWは gdi32 の `SwapBuffers` を呼び、`wglSwapBuffers` はその先で呼ばれる。
   GLFWの関数ならLinuxでも同じ場所でフックでき（GLX／EGLの違いを気にしなくてよい）、`GLFWwindow*` も直接取れる。
   自前のコンテキストは引き続きWGL（Linuxでは GLX／EGL）で作る。
6. **フックの中でパニックを外に出さない**
   Rustのパニックが `extern "C"` の境界を越えるとプロセスごと終了する（＝ゲームがクラッシュする）。
   すべてのフックを `catch_unwind` で包み、失敗したら元の関数にそのまま渡す。エラーはログに残し、オーバーレイを止めるだけにする。

### 入力まわりの方針

- UIを開いている間も、キーとマウスボタンを「離した」イベントはMinecraftに渡す。渡さないと、Wを押したままUIを開いて離したときに歩き続ける
- UIを開くときにカーソルを `DISABLED` から `NORMAL` に切り替えると、閉じたときにMinecraftが大きなマウスの移動と受け取り、視点が飛ぶことがある。
  閉じる前にカーソルの位置を戻すか、`DISABLED` のまま自前のカーソルを描いて相対移動で動かす方式を試す
- ホットキーは、カーソルが `DISABLED`（ゲームを操作している状態）のときだけ反応させる。チャットに入力している最中に誤って発動せず、この判定もバージョンに依存しない

### 要確認（Minecraft本体の挙動についての記憶。jarでは未確認）

- 文字入力には `glfwSetCharCallback` ではなく `glfwSetCharModsCallback` を使っていたはず → 両方をフックする
- F3+C について
  - ゲームルール `reducedDebugInfo` が有効なワールドやサーバーでは効かず、座標を取れない（既知の制約）
  - Minecraftの画面（チャット、インベントリ、ポーズなど）が開いている間は効かない
  - 1.21.9前後でF3系のキーをキー設定で変えられるようになったはずで、F3の判定が `glfwGetKey` ではなくキー割り当ての状態に変わっている可能性がある
  - 対策として「F3↓ → C↓ →（クリップボードへの書き込みを待つ）→ C↑ → F3↑」をコールバックで数フレームに分けて送り、`glfwGetKey(F3)` の偽装も併用する。これならどちらの判定でも動くはず
- マルチプレイの接続先は `logs/latest.log` の `Connecting to <host>, <port>` の行から取る。1.16以前はSRVレコードを解決した後のホスト名が出る可能性がある

## 追記：プロトタイプ1で分かったこと（2026-09-29）

### フックのクレートは MinHook にした
`retour` 0.3.1 は、RIP相対のアドレスの後ろに即値が続く命令を正しく移せない（変位を「命令の最後の4バイト」とみなして書き換える。`retour/src/arch/x86/trampoline/mod.rs` の `instruction_bytes.len() - 4`）。
GLFWのAPI関数の多くは、最初の数バイトの中で初期化済みかを調べる `cmp dword [rip+_glfw.initialized], 0`（`83 3d <disp32> 00`）を実行する。
`glfwSwapBuffers` では先頭の命令そのもので、`glfwSetKeyCallback`・`glfwSetCharModsCallback`・`glfwGetKey` などでは `sub rsp,28h` の直後（+4バイト）にある（LWJGL 3.1.6／3.2.2／3.3.3 の glfw.dll で確認）。
どちらもフックで書き換える先頭5バイトにかかるため、トランポリンに移される。このため `retour` でフックすると、元の関数を呼んだ瞬間に不正なアドレスを読んで落ちる（Wine上で再現を確認）。
MinHook は即値の長さを差し引いて変位の位置を求めるので問題ない。Windows では `minhook` クレートを使う。Linux対応のときは別の方法（`retour` の修正版など）を検討する。

### Wine上で確かめたこと（`scripts/wine-smoke.sh`）
実機のWindowsではなく、Wine 9.0 と Mesa llvmpipe での結果。
- `-agentpath:` で `Agent_OnLoad` が呼ばれ、`LdrRegisterDllNotification` の通知がすべてのDLLについて届く
- LWJGLは `glfw.dll` を `GLFW` クラスの初期化時（`glfwInit` の前）に読み込む。ファイル名はいつも `glfw.dll`で、場所は起動方法で変わる
  - `-Dorg.lwjgl.system.SharedLibraryExtractPath` があればそのフォルダ（公式ランチャー 1.19以降の `natives`）
  - なければ `%TEMP%\lwjgl_<ユーザー>\<バージョン>\x64\glfw.dll`（3.2.2 は `%TEMP%\lwjgl<ユーザー>\3.2.2-build-10\glfw.dll`）
  - `java.library.path` で見つける場合はそのフォルダ（1.18以前の公式ランチャー、Prism、MultiMC）
- `opengl32.dll` は `glfwCreateWindow` の中で読み込まれる。`glfwTerminate` の後も `glfw.dll` と `opengl32.dll` は解放されない
- 通知の中でGLFWのエクスポートを調べてフックを入れられる（エクスポート表は `GetProcAddress` を使わず、PEのヘッダーから直接読む）
- 同じHDCに作った自前のコンテキスト（Compatibility Profile）で egui を描き、ゲームのコンテキスト（Core Profile 3.2）に戻せる。ゲーム側のGLのエラーは増えず、終了時の `glfwFreeCallbacks` でも落ちない

## 追記：Minecraft 26.x はGLFWを使っていない（2026-09-29）

実機（Prism Launcher、Minecraft 26.3、バニラ、Java 25 の `java-runtime-epsilon`）で試したところ、`glfw.dll` は読み込まれず、LWJGL 3.4.3 の `SDL3.dll` が読み込まれた。
ウィンドウと入力はGLFWからSDL3に替わったとみられる。あわせて `vulkan-1.dll`・`shaderc.dll`・`spirv-cross.dll`・`lwjgl_vma.dll` と、NVIDIAのOpenGLドライバ（`nvoglv64.dll`）も読み込まれている。
1.21.11 は従来どおりGLFWで起動する。

- 「1.13以降はGLFW」という前提は 26.x では成り立たない。26.x は個別に対応する
- 描画がOpenGLなら、`SDL_GL_SwapWindow` のフックに付け替えればほぼ同じ方式で描ける。Vulkanなら `vkQueuePresentKHR` をフックしてVulkanで描く必要があり、描画部分の作り直しになる
- どちらかを確かめるため、いまのエージェントはSDL3を検出すると `SDL_CreateWindow`（フラグ）・`SDL_GL_CreateContext`・`SDL_Vulkan_CreateSurface`・`SDL_GL_SwapWindow` を診断用にフックし、結果をログに出す（`renderer: OpenGL via SDL3` など）。描画はしない
- 検証用に `ci/smoke/SmokeSdl.java`（SDL3でOpenGLのウィンドウを作る）を追加し、CIとWine（`scripts/wine-smoke.sh --sdl --lwjgl 3.4.3`）で確かめている

### 26.3 の結果と対応（2026-09-29）
- 実機のログ：`Minecraft - RenderPearl OpenGL Hidden Utility Window` と `... Hidden Test Window`（どちらも OpenGL・非表示）を作り、補助ウィンドウで `SDL_GL_CreateContext` を1回呼ぶ。続いて `Minecraft 26.3`（OpenGL）を作り、毎フレーム `SDL_GL_SwapWindow` を呼ぶ。Vulkanのサーフェスは作られない
- つまり描画はOpenGL。コンテキストは非表示の補助ウィンドウで作り、ゲームのウィンドウで使っている
- 対応：描画部分（`hook-win/src/frame.rs`）をウィンドウのライブラリに依存しない形（`WindowSystem` トレイト）にし、GLFWとSDL3の両方から呼ぶ。SDL3では `SDL_GL_SwapWindow` をフックし、HWNDは `SDL.window.win32.hwnd` プロパティ、大きさは `SDL_GetWindowSizeInPixels`、倍率は `SDL_GetWindowDisplayScale`、非表示の判定は `SDL_GetWindowFlags` で取る
- `ci/smoke/SmokeSdl.java` は26.3と同じ手順（非表示の補助ウィンドウでコンテキストを作り、ゲームのウィンドウで使う）にした。Wineで表示を確認済み

## 追記：プロトタイプ2（入力・ホットキー・ズーム）の設計（2026-09-29）

- ホットキー：Ctrl+I でメニューを開閉（どの画面でも有効）、Esc で閉じる、Z を押している間ズーム（ゲーム中＝カーソルを捕まえているときだけ。チャットでは効かない）。設定の保存は未実装
- 入力の振り分けは `render/src/input.rs` の `InputRouter`（OSに依存しない。単体テストあり）。GLFWとSDL3のフックは、イベントを渡して「ゲームに渡す／横取りする」の答えに従うだけ
  - メニューを開いている間は、押したイベントを横取りし、離したイベントはゲームに渡す（押しっぱなしの状態が残らないように）
  - オーバーレイが描けていないとき（`overlay=off`、初期化の失敗、フレーム中のパニック）は何も横取りしない。見えないメニューが入力を奪うことはない
- マウス：カーソルを捕まえたまま（GLFW の `CURSOR_DISABLED`、SDL3 の相対マウスモード）、自前の矢印を描いて相対移動で動かす。ゲームのカーソルの状態は切り替えない
  - GLFW は捕まえたカーソルの位置を、どこまでも増える仮想の座標で報告し、ゲームは前回との差で視点を回す。メニューを開いている間に動いた量を覚えておき、閉じた後にゲームへ渡す座標から差し引く（閉じた瞬間に視点が飛ばない）。ゲームがカーソルを捕まえ直したり放したりしたら、この補正は捨てる
- GLFW：`glfwSet{Key,Char,CharMods,MouseButton,CursorPos,Scroll,WindowFocus}Callback` をフックし、GLFWには自前のラッパーを登録する。戻り値にはゲームが前に登録したポインタを返す（終了時の `glfwFreeCallbacks` 対策）。ゲーム中かどうかは `glfwGetInputMode(CURSOR)` で判定
- SDL3：`SDL_PollEvent` をフックし、横取りするイベントは取り除いて次のイベントを返す。メニューを開いている間は `SDL_StartTextInput` で文字入力（とIME）を有効にし、閉じたら元に戻す。ゲームが別の経路で入力を読む可能性があるので、`SDL_PeepEvents`・`SDL_WaitEvent(Timeout)`・`SDL_GetKeyboardState`・`SDL_GetMouseState`・`SDL_GetRelativeMouseState`・`SDL_AddEventWatch`・`SDL_SetEventFilter` を最初に使ったときと、`SDL_SetWindowRelativeMouseMode` の呼び出しをログに記録する
- ズーム：`render/src/zoom.rs`。中央部分を同じ大きさで自前のFBOにコピーしてから、画面全体に引き伸ばす（2段階）。eguiが有効のまま残すscissor testをblitの前に切る。GL 3.0 未満では使わない
- Wine上で `xdotool` により実際のキー・マウス操作を送って確認した（GLFW・SDL3の両方）：Ctrl+I で開閉、テキスト欄への入力、ゲームには離したイベントだけが届くこと、ズーム。カーソルを捕まえた状態のマウスの相対移動は、Wine+Xvfbでは届かないため未確認

### 実機での指摘と修正（2026-09-29）

メニューを開けることは実機で確認できた。指摘された 2 点を直した。

- **チェックボックスと文字の高さがずれる**：egui は、フォントの ascent・descent・line gap から行の高さを決め、ascent の位置に基準線を置き、行をチェックボックスの中央に合わせる。
  游ゴシックは line gap が大きいので、文字が行の上のほうに寄り、チェックボックスより高く描かれていた。
  日本語フォントを読み込むときに、egui と同じ値（skrifa の metrics）から「行の中央」と「文字の中央（基準線から 0.38 em 上）」の差を求め、`FontTweak::y_offset_factor` で文字を下げる（`render/src/font_metrics.rs`）。
  Wine で line gap の大きいフォント（IPA ゴシックの hhea を 0.88／−0.12／0.72 em に変えたもの）を使うと実機と同じずれが出て、修正後は中央に揃うことを確かめた。egui 内蔵のフォントでは差がほぼ 0（0.02 em）になる
- **メニューのカーソルの速度に Windows の設定が反映されない**：ゲームは、カーソルを捕まえている間、Windows のポインターの速度も加速もかかっていない生の移動量（raw input）を読む。自前のカーソルはこれで動かしていたので、デスクトップと速さが違った。
  メニューを開くたびに `SPI_GETMOUSESPEED`（1〜20）と `SPI_GETMOUSE`（「ポインターの精度を高める」）、加速の曲線（`HKCU\Control Panel\Mouse` の `SmoothMouseXCurve`／`SmoothMouseYCurve`）を読み、移動量に掛ける（`render/src/pointer.rs`、`hook-win/src/pointer.rs`）。
  計算は SDL3 の `SDL_HINT_MOUSE_RELATIVE_SYSTEM_SCALE` と同じ（精度を高めるがオフなら速度ごとの倍率、オンなら 1 回の移動量に応じた曲線。Windows 本来の計算の近似）
  - ゲームがすでに Windows の速度のかかった移動量を読んでいるときは掛けない：GLFW 3.3 以降で `GLFW_RAW_MOUSE_MOTION` がオフ（Minecraft の「Raw Input」がオフ）のとき、SDL3 でヒント `SDL_MOUSE_RELATIVE_MODE_WARP` か `SDL_MOUSE_RELATIVE_SYSTEM_SCALE` がオンのとき。
    `glfwRawMouseMotionSupported` のない GLFW（LWJGL 3.1.6 の 3.3.0 の開発版）は、捕まえたカーソルでは常に raw input を使う

## 追記：高精細のズーム・キーの変更・設定の保存（2026-09-29）

主要なズーム Mod と同じく、画面全体を拡大する（枠の中だけを拡大する形式ではない）。描かれた画面を引き伸ばすのではなく、細かいところまで見えるようにした。

### 高精細のズーム（`hook-win/src/tall.rs`）

Minecraft の視野角は縦方向で決まる。同じ幅で縦に k 倍長い解像度で描かせると、1 度あたりの画素が縦横とも k 倍になり、その中央の部分（元の画面と同じ大きさ）が k 倍に拡大した絵になる。FOV を変えるのと同じ効果を、ゲームのコードに触れずに得られる（スピードランの縦長の解像度と同じ）。

ズームキーを押している間だけ、次の 3 つを行う。

1. **ゲームに縦長の大きさを伝える**：GLFW はゲームが登録したフレームバッファの大きさのコールバックを呼び、`glfwGetFramebufferSize` の結果も差し替える。SDL3 は `SDL_EVENT_WINDOW_PIXEL_SIZE_CHANGED` と `SDL_EVENT_WINDOW_RESIZED` のイベントを `SDL_PollEvent` から渡し、`SDL_GetWindowSizeInPixels` の結果も差し替える。ゲームはふつうのリサイズと同じように描画先を作り直す（Minecraft は `resizeDisplay` の中でマウスの基準も取り直すので、視点は飛ばない）
2. **ゲームのウィンドウへの出力を自前のフレームバッファに受ける**：縦長の出力はウィンドウに入りきらず切り捨てられる。opengl32.dll が読み込まれた時点で `wglGetProcAddress` をフックし、ゲームには `glBindFramebuffer`・`glBindFramebufferEXT`・`glBlitNamedFramebuffer` の代わりに、フレームバッファ 0 を自前のもの（縦長の大きさ）に差し替える関数を渡す。LWJGL も SDL3 も GL 3.0 以降の関数はこの関数で探すので、バージョンに依存しない
3. **バッファの入れ替えのときに、自前のフレームバッファの中央をウィンドウにコピーする**（ゲームのコンテキストで。触った状態は元に戻す）

- ゲームが本当に縦長で描いたかは、`glViewport` もラップして確かめる（GL 1.1 の関数なので多くのドライバーでは `wglGetProcAddress` が null を返すが、それでもラッパーを渡す）。3 フレーム以上かつ 1 秒以上続けて縦長で描かれなかったら、そのセッションでは高精細をやめて、引き伸ばす拡大にする（当初は 3 フレームだけで判定していた。描画先を縦長で作り直す間にゲームが数フレーム止まっても見切らないよう、余裕を持たせた。実機では 1.21.11 は高精細で拡大できたが、26.3 は押してから 0.12 秒で見切った。26.3 の原因が待ち時間かは未確認）
- 大きさを変えている間にウィンドウの本当の大きさが変わったら、その通知はゲームに渡さずにズームを終え、新しい大きさを伝え直す
- ゲームがカーソルを放したら（Z を押したままインベントリを開いた）ズームを終える
- 描く画素が倍率ぶん増える（2560×1440 で 4 倍なら 2560×5760）。倍率の上限は `GL_MAX_TEXTURE_SIZE` などで決まる
- 押した瞬間と離した瞬間にゲームが描画先を作り直すので、一瞬引っかかることがある。そのため、なめらかに倍率を変えるアニメーションはできない
- 拡大している間は画面の下の HUD が見えない（縦長の画面の下端に描かれる）
- Wine で確認した：GLFW（LWJGL 3.3.3 のコアプロファイル、3.2.2 の互換プロファイル）と SDL3（3.4.3）の両方で、テスト用のプログラムが Minecraft と同じように自前のフレームバッファに描いて最後にウィンドウへ転送するとき（`--mc`）に、4 倍で細部まで拡大されること。ゲームがウィンドウに直接描くとき（フックを通らない）は 3 フレームで引き伸ばす拡大に切り替わること
- 26.x は実機のコードを見られていないので、ゲームがリサイズのイベントに反応するかが未確認

### キーの変更と設定の保存

- ホットキーはキー（修飾キー付き）かマウスのボタン（ホイールクリック、ボタン 4・5）。設定ファイルには `"Ctrl+I"`・`"Z"`・`"Mouse4"` のように文字で保存する（egui のキーの名前）。Esc と修飾キーだけは割り当てられない
- ホットキーの修飾キーは「押されていること」だけを見る。余分な修飾キーが押されていても反応する（Ctrl でダッシュしながらズームできる）。そのため、メニューのキーがズームのキーを隠してしまう組み合わせ（例：メニューが Z、ズームが Ctrl+Z）は受け付けない
- メニューでボタンを押すと、次に押したキーを割り当てる（入力の振り分けで横取りし、egui にもゲームにも渡さない）。Esc で取り消し
- キーの表は F1〜F25、記号、テンキーまで広げた（GLFW はアメリカ配列の位置、SDL3 は配列に従った文字）
- 設定はゲームフォルダの `reminedog/settings.json`（`core/src/settings.rs`）。知らない項目は無視し、ない項目は既定値にするので、バージョンが変わっても読める。壊れたファイルは `settings.corrupt-<時刻>.json` に移す。メニューで変えてから 1 秒たつか、メニューを閉じたときに保存する

### 26.3 で高精細にならなかった原因（2026-09-29）

- 実機の 26.3（ウィンドウ 2561×1440、表示スケール 125%）で、Z を押すと高精細にならず引き伸ばす拡大になった。1.21.11 では高精細で拡大できた
- `=log=debug` のログ：ゲームの出力は毎フレーム自前のフレームバッファに届き、ゲームは `glViewport` で 2560×4320 を指定していた。こちらが伝えたのは 2561×4320 で、判定は幅まで一致を求めていたので、縦長で描いていないとみなしていた
- ゲームは SDL が報告する 2561 px ではなく、自分の幅（2560）を使い続ける。26.3 は `SDL_GetWindowSizeInPixels` を呼ばず、大きさの変更のイベントの値を使う
- 判定は高さだけにした（縦に k 倍の高さは、ズーム以外では使われない）。26.3 の実機で高精細に拡大できることを確認した

### 最小化中にオーバーレイを作り直し続けていた（2026-09-29）

- 実機の 1.21.11 で、全画面から Alt+Tab で抜けて最小化されている間、スワップのたび（10 fps）に「the game's device context changed」と出て、オーバーレイのコンテキストを作り直していた（27 秒で 266 回）
- 原因：GLFW と SDL3 のウィンドウは CS_OWNDC なので、`GetDC` はいつも同じ DC を返す前提だった。最小化中は、`GetDC` が呼ぶたびに別の一時的な DC を返す（ゲームのコンテキストは元の DC のまま）。DC が変わったとみなして作り直し、一時的な DC を解放していなかったので GDI のハンドルも漏れていた
- 対応：ウィンドウが最小化されている（`IsIconic`）間は、スワップのフックで何もしない。オーバーレイはそのまま残し、戻したら続きから描く
- Windows 上で LWJGL 3.3.3（GLFW）と 3.4.3（SDL3）のテスト用プログラムを動かし、`ShowWindow` で最小化して戻して確認した（修正前は GLFW 版で再現）

## 追記：プロトタイプ 3（F3+C によるウェイポイント）（2026-09-30）

ゲーム中に J で今いる場所をウェイポイントとして記録し、K で目的地（メニューで選んだ地点）への方角と距離を出す。
座標は、reminedog がゲームに F3+C のキーを送り、Minecraft がクリップボードに書く文字列を横取りして取る。最初の設計の「座標の取得（F3+C）」を、jar で確かめた挙動に合わせて作り直した。

### ゲームの挙動（jar で確認）

利用者のインスタンスのクライアントの jar（1.16.1、1.21.11、26.3）を javap で読んで確かめた。ゲームを動かしての確認ではない。

- 出力は `/execute in <ディメンション> run tp @s x y z yaw pitch`（`Locale.ROOT`、小数 2 桁、yaw は ±180 に収めない）。3 つの版で同じで、`core::parse_f3c` で読める
- F3 を押しているかの判定
  - 1.16.1：C のキーのイベントを処理するときに `glfwGetKey(window, 292)`（F3）を読む。F3 と C（67）は固定
  - 1.21.11（GLFW）と 26.3（SDL3）：キー設定 `key.debug.modifier` の Java 側の状態。そのキーの押下のイベントで立ち、ネイティブのキーの状態は読まない。座標のコピーは `key.debug.copyLocation`、クラッシュは `key.debug.crash`。
    どれもキー設定で変えられ、options.txt に `key_key.debug.modifier:key.keyboard.f3`・`key_key.debug.copyLocation:key.keyboard.c`・`key_key.debug.crash:key.keyboard.c` のように保存される。1.21.11 は GLFW のキーコード、26.3 は SDL のスキャンコードで照合する
  - 上の「未検証の前提」の F3 の判定の件と、「要確認」の 1.21.9 以降の変化は、これで分かった
- キーのイベントは描画のスレッドで同期して処理される（`minecraft.execute` がその場で実行する）。GLFW では C の押下のコールバックの中で、SDL3 では次の `SDL_PollEvent` の前に、クリップボードに書く。なので、書き込みを送ったキーに結び付けられる
- 成功したとき：C には `set(false)` だけが送られ、C に割り当てたほかの操作は動かない。修飾キーを離しても F3 画面は切り替わらない
- 拒否されるとき（プレイヤーがいない、またはサーバーかゲームルール `reduced_debug_info` でデバッグ情報が制限されている。クライアントの設定の「デバッグ情報を減らす」は関係しない）
  - クリップボードに書かない
  - C は処理されなかった押下になり、C に割り当てたすべての操作に `set(true)` と `click` が送られる。利用者の 26.3 と 1.16.1 の options.txt は `key_key.drop:key.keyboard.c` なので、手に持ったアイテムを 1 個捨てる（Ctrl を押していればスタックごと。Ctrl は実際のキーの状態で読まれる）。
    1.21.11 の既定では「ホットバーの保存」（key.saveToolbarActivator）も C だが、押している間の状態しか見ないので害はない（押下と解放が同じポーリングの中で届くので、tick で押されているとは読まれない）。
    そのため、押している間の状態しか見ない操作（前後左右、ジャンプ、プレイヤーリスト、ホットバーの保存と読み込み）は、共有の警告に出さない
  - 続けて修飾キーを離すと F3 画面が切り替わる。修飾キーの押下と解放をもう一度（この順で）送ると元に戻る。1.16.1 では、そのときの Shift と Alt の状態でグラフの表示も作り直される
  - 本物の F3+C では、拒否されても切り替わらない。C を実際に押すとクラッシュのタイマーが動き、そのときに立つフラグが切り替えを抑えるため。送った C ではタイマーは動かない
- デバッグのクラッシュ：修飾キーが押されている間に、crash のキーが実際に押されていると（1.21.11 は `glfwGetKey`、26.3 は `SDL_GetKeyboardState` で読む）タイマーが動き、10 秒でゲームを落とす。タイマーが動いて 100 ms を過ぎると、デバッグのキーは何もしなくなる（本物の F3+C を押し続けてもコピーは 1 回だけ）
- キーのイベントには、ゲームのウィンドウが入っていなければならない（GLFW はウィンドウのハンドル、SDL3 は `windowID`。違えば無視される）
- 画面（チャット、インベントリなど）が開いているときは送らない。画面がキーを受け取ると、修飾キーが押されたまま残ることがある
- 送るたびに、チャットに「［デバッグ］：クリップボードに座標をコピーしました」（en_us は "[Debug]: Copied location to clipboard"）が出る。ゲームが出すので消せない。1.21.11 と 26.3 ではナレーターにも渡る
- latest.log：1.21.11 と 26.3 は `[Server thread/INFO]: Starting integrated minecraft server version …` と `Stopping server`、マルチプレイでは `Connecting to <host>, <port>` を出す（ゲームの言語が日本語でも英語）。
  log4j は起動時（エージェントの最初のフレームより前）と、プレイ中に日付が変わったときに latest.log を作り直す
- バニラの 1.16.1 のサーバーのスレッドの名前は `Server thread`。利用者の 1.16.1 は Fabric のスピードラン用の構成（SeedQueue など）で、裏で統合サーバーを何度も起動し、スレッドの名前も変わる（`Server thread #N`）。この構成ではワールドを判定できない（対象外）

### 設計

**キー**
- 記録キー（既定 J）と現在地を更新キー（既定 K）を足した。settings.json の `waypoint_key`・`navigate_key`。ゲーム中（カーソルを捕まえていて、メニューを閉じている）だけ反応し、押下をルーターのキュー（`HotkeyAction`、最大 4 件）に入れる。フレームの処理がそれを F3+C の要求にする
- Minecraft の修飾キー（options.txt の割り当て。既定は F3）を押している間は、J・K・ズームのキーをゲームに渡す。F3+… の組み合わせを奪わない（ズームを C にしていても、本物の F3+C は効く）
  - ズームのキーを修飾キーそのもの（F3）にしているときは、ズームとして扱う（その間 J・K はゲームに渡る）。ズームはリピートでは始めない（修飾キーを押している間にゲームへ渡した押下の、解放もゲームに渡すため）
- メニューでキーを割り当てるときは、4 つのキーのどの組でも、ルーターが先に調べるキーが後のキーを隠すなら拒む（調べる順はメニュー、記録、更新、ズーム）。
  記録キーと更新キーには、options.txt の修飾キー・座標のコピー・クラッシュのキーも割り当てられない（押したまま送ることになり、必ず失敗する）
- K は、目的地を選んでいなければ F3+C を送らず、「目的地が選ばれていない（メニューで選ぶ）」とだけ出す（送ってもチャットに行が出るだけ）。メニューの「現在地を更新」は、目的地がなくても送る

**F3+C の要求と結果（`hook-win/src/f3c.rs`）**
- 要求はフレームの処理が出し、プラットフォームの次の機会に取られる（GLFW はそのウィンドウのスワップの後、SDL3 は次の `SDL_PollEvent`）。取ったらその場で最後まで送り、結果を返す。
  2 秒たっても取られないか、取られたのに次のフレームで終わっていなければ、時間切れにする（パニックなどで取り残されても、要求中のままにならない）
- 送る前に確かめること。1 つでも満たさなければ、送らずに失敗を通知する
  - クリップボードのフック、キーを送るためのフック（GLFW はキーコールバック、SDL3 は `SDL_PollEvent`）、実際のキーの状態を読む関数（`glfwGetKey`、`SDL_GetKeyboardState`。SDL3 は `SDL_GetWindowID` も）が揃っている。
    クリップボードのフックがないと、成功しても書き込みが見えずに拒否とみなし、元に戻すための押下で F3 画面を開いてしまう
  - ゲームがカーソルを捕まえている（画面が開いていない）
  - 修飾キー・座標のコピーのキー・クラッシュのキーのどれも、実際には押されていない。C に「アイテムを捨てる」もあるときは、左右の Ctrl も。クラッシュのタイマー、本物の修飾キーの解放による F3 画面の切り替え、拒否されたときにスタックごと捨てることを防ぐ。
    Ctrl を見るのは捨てる操作があるときだけにした（1.21.11 の既定では Ctrl がダッシュのキーで、走りながら K を押すことが多い）。記録キーと更新キーは Ctrl との組み合わせにできない（押した Ctrl が送るときまで残るため）
  - options.txt のキーが送れるものである（英字、数字、F1〜F25（SDL3 は F24 まで）、テンキーの数字）。修飾キーか座標のコピーが未割り当てなら送れない。options.txt は 5 秒ごとに読み直す（行がない版では既定の F3・C）
- 送る順は、修飾キーの押下、コピーのキーの押下、コピーのキーの解放、修飾キーの解放（Shift などの状態は付けない）
- コピーのキーの押下から修飾キーの解放までを「注入の窓」とし、その間のクリップボードへの書き込みで結果を決める
  - 座標として読めた：成功。書き込みは OS に渡さないので、利用者のクリップボードは変わらない
  - 書き込みはあったが読めない（Mod のディメンションなど）：書き込みは握りつぶし、「座標を読み取れなかった」と出す。ゲームはキーを処理したので、元に戻す操作はしない
  - 書き込みがない：拒否。修飾キーの押下と解放をもう一度送って F3 画面を戻し、そのワールドでは以後送らない（メニューの「もう一度試す」かワールドの切り替えまで）。送るたびに C の操作が動くのを防ぐため。利用者自身の F3+C で座標が取れたら、止めるのをやめる
- GLFW（`glfw_input.rs`）：`glfwSetClipboardString` と `glfwGetKey` をフックする。キーはゲームのキーコールバックを直接呼んで送る（ルーターを通らない）。送る間だけ、`glfwGetKey(ウィンドウ, 修飾キー)` に押していると返す（1.16 向け。C は偽装しない）。
  手順全体を RAII のガードで包み、パニックしても偽装を消し、押した修飾キーを離す。スキャンコードは `glfwGetKeyScancode` で引く（なければ 0）
- SDL3（`sdl_input.rs`）：`SDL_SetClipboardText` をフックする。`SDL_PollEvent` のフックが先に返す注入のキュー（`INJECTED`）に、4 つのキーのイベントを積む（`windowID` はゲームのウィンドウ、スキャンコードはオフセット 24、キーコードも入れる）。
  コピーの押下を返すときに注入の窓を開き、修飾キーの解放を返すときに閉じて判定する。拒否なら、修飾キーの押下と解放をキューの先頭に入れる（押下が先に出るように、解放から先に入れる）
- 利用者自身の F3+C：ゲームにコピーのキーの押下を渡すときに「受け身の窓」を開く（GLFW はコールバックに転送している間、SDL3 はその押下を返してから次の `SDL_PollEvent` まで）。
  その間の書き込みが座標として読めたら現在地にする。書き込みは OS に渡す。チャットのクリックでのコピーや、入力欄の Ctrl+C は拾わない
- クリップボードのフックは、どちらの窓も開いていなければ、何も確保せずに元の関数を呼ぶ。512 バイトを超える書き込みは解析しない
- ロックの順序：`router → f3c` と `INJECTED → f3c` は可。f3c のロックを持ったまま、ほかのロックを取らず、ゲームのコードも呼ばない。`take_job` は `INJECTED` をロックする前に呼ぶ

**ワールドとウェイポイント（`hook-win/src/waypoints.rs`、`core/src/session.rs`）**
- 状態は static に置く（ゲームの DC が変わってオーバーレイの `Runtime` を作り直しても残る）。スワップの経路から毎フレーム、オーバーレイを描く前に次を行う
  1. 1 秒ごとに latest.log を読む（`WorldWatcher`）。ワールドが変わったら、そのワールドのウェイポイントを開き、目的地・現在地・拒否の状態を消す
  2. 5 秒ごとに options.txt を読む
  3. F3+C の結果を、ウェイポイントと通知にする。座標が届いたら、先に latest.log を読んでワールドの切り替えを済ませてから保存する
  4. ホットキーの押下（ゲーム中のときだけ）とメニューの操作を、要求にする
- ワールドの判定：統合サーバーが起動したら `saves/*/session.lock` の最も新しいワールド、`Connecting to` ならそのサーバー、`Stopping server` なら「ワールドに入っていない」。
  起動したのにワールドのフォルダが見つからなければ「判定できていない」とし、記録のときにもう一度探す。プレイ中に latest.log が作り直されても、判定は保つ
- 保存先は `<ゲームフォルダ>/reminedog/waypoints/sp-<ワールドのフォルダ名>.json`（サーバーは `mp-<ホスト>-<ポート>.json`）。変更のたびにすぐ保存する（一時ファイルに書いて置き換える）。
  保存に失敗しても変更はメモリに残し、メニューに警告を出して、次の変更のとき（と 10 秒ごと）に保存し直す。ワールドを切り替えるときにも保存できなければ、変更は失われ、通知で知らせる。壊れたファイルは `<名前>.corrupt-<時刻>.json` に移し、メニューに出す。
  シングルプレイはフォルダ名で区別するので、ワールドを消して同じ名前で作り直すと、前の地点が出る（ワールドを見分ける情報は保存していない）
- 名前は「地点 N」（N はワールドごとの通し番号）。メニューで変えられる（空の名前にはできない）
- 方角と距離（`core::nav::guide`）：通知では、F3+C の向きからの左右の角度も出す。メニューの一覧は方角・距離・高さだけ（向きは座標を取った時点のもので、メニューを見る時には古い）。
  （2026-09-30 追記）利用者の要望で、方角を矢印でも示すようにした（K の通知、メニューの一覧、下の画面左の表示）。矢印は座標を取ったときの向きを上とし、F3+C のときだけ変わる。
  マウスの動きから向きを推定することも検討した（26.3 の `MouseHandler.turnPlayer` は感度 s から `(0.6s+0.2)^3×8`、`Entity.turn` で 0.15 倍）が、滑らかなカメラ・乗り物・テレポートなどでずれるので入れていない。利用者も F3+C のときだけの更新でよいとした
- 画面左の目的地（`render/src/waypoints.rs` の `draw_destination`）：目的地を選んでいてメニューを閉じている間、左の中ほど（`LEFT_CENTER`）に、名前、ディメンションと座標、最後の現在地からの方角・距離・高さ、「N 秒前の位置と向きから」、大きな矢印を出す。
  現在地を取っていなければ「現在地が未取得（K で更新）」。矢印は `egui::Shape::convex_polygon` で描く（頭の三角形と軸の四角形。egui の凸多角形は時計回りに並べる）
  オーバーワールドとネザーの間は x・z を 1:8 で換算し、換算した座標を添える（y は換算しない）。ジ・エンドなど、ほかの組み合わせは「別のディメンション」とだけ出す
- 通知：画面の上から約 22% の位置（クロスヘアより上。GUI の大きさ 5 ではボスバーとプレイヤー一覧が上端から約 85 px まで使うので、その下）に、`Order::Foreground` で描く（メニューより手前）。最大 3 つ、6 秒（方角と距離は 8 秒）。メニューを閉じていても出す
- メニュー：「入力のテスト」の欄をなくし、「ウェイポイント」の欄にした。IME の確認は名前の変更の欄で行う。
  名前の編集中の文字と削除の確認は、メニューを閉じたときとワールドが変わったときに消す（ID はワールドごとに 1 から振るので、別のワールドの地点を消さないように）
- `overlay=off` のときや、オーバーレイが無効になったときは、ウェイポイントも動かない（処理がスワップの描画の経路にあるため）

### スモークテスト（`ci/smoke`）

- `--world=<名前>`（Smoke と SmokeSdl）：作業フォルダに `logs/latest.log`（統合サーバーの起動の 1 行）と `saves/<名前>/session.lock` を書く。エージェントに `gamedir=` を付けなければ、作業フォルダがゲームフォルダになる。記録できれば `reminedog/waypoints/sp-<名前>.json` ができる
- `--f3c-refuse`（両方）：F3+C でコピーしない（デバッグ情報の制限の再現）
- `--f3c-events`（Smoke だけ）：1.21.9 以降と同じく、修飾キーをキーのイベントだけで追う。既定は 1.16 と同じ `glfwGetKey`。SmokeSdl は 26.3 と同じくイベントで追う
- 終了時に `F3C STATE overlay=<on|off> modifier=<up|down> copies=<n>` を出す。記録が成功すれば `overlay=off modifier=up copies=1`、`--f3c-refuse` なら `overlay=off modifier=up copies=0`（途中に `F3C overlay on` と `F3C overlay off`）。どちらでも `F3C crash armed` が出てはいけない
- 手元で本物の F3+C を試すとき、PowerShell の `SendKeys` では F3 を押したまま C を押せない。`Add-Type` で `SendInput` を使う
- CI はまだ新しいオプションを使っていない。クリップボードのフックが入ったことは、ログの `F3+C: clipboard hooks ready` で分かる

- 1.13〜1.15 と 1.17〜1.21.8 の jar は見ていない。1.16.1 と同じ判定（`glfwGetKey`）でも、1.21.11 と同じ判定（キー設定の状態）でも動くように送っている
- IME の変換を確定する Enter で、名前の変更まで決定されないか
- 修飾キーを F3 以外に変えたとき。修飾キーを F3 画面のキーと別にすると、修飾キーを離しても F3 画面は切り替わらない（F3 画面のキーの押下で切り替わる。reminedog はそのキーを送らない）

## 追記：キーの置き換え（2026-10-02）

ゲーム中だけ、Minecraft に届くキーやマウスのボタンを、別のキーやマウスのボタンに置き換える（例：マウスのボタン4 → F3、CapsLock → 左 Ctrl、マウスのボタン5 → C）。Toolscreen のキーの置き換え（Key Rebinds）に当たる。
キー → キー、マウス → キー、キー → マウス、マウス → マウスのどれもできる。置き換えた出力はもう一度置き換えない（A と B を入れ替えられる）。

### ゲームとライブラリの挙動（jar とソースで確認）

利用者の jar（1.16.1、1.21.11、26.3）の javap と、GLFW 3.4・SDL 3.4.0 のソースで確かめた。ゲームを動かしての確認ではない。

**26.3（SDL3）**
- キーは SDL のスキャンコード、マウスのボタンは SDL の番号（左 1、中 2、右 3、4、5）で照合する。キーのイベントから読むのは type・windowID・scancode・key（キーコード）・mod・repeat。ボタンのイベントからは type・windowID・button だけ（down・clicks・which・位置は読まない）
- クリックの修飾キーは、イベントを処理するときに `SDL_GetModState()` を呼んで読む（イベントの中身ではない）
- 本物の状態を読むのは `SDL_GetKeyboardState()[scancode]`（`InputConstants.isKeyDown`）と `SDL_GetModState` だけ
  - `isKeyDown`：画面を閉じたときの `KeyMapping.setAll()`（キーボードの割り当てだけを読み直す。トグルのモードの割り当ては除く）、Ctrl（スタックごと捨てる、ブロック選択でデータ付き）、Shift、デバッグのクラッシュのキー
  - `SDL_GetModState`：クリックの修飾キーと Alt+F4 の判定
  - マウスのボタンの状態は読まない（`SDL_GetMouseState` は位置だけ）
- 画面を開くと `KeyMapping.releaseAll()`、閉じると `setAll()`。Java 側でフォーカスを失ったときに割り当てを離すのは、`pauseOnLostFocus` の一時停止画面（500 ms 後）だけ

**1.21.11・1.16.1（GLFW）**
- キーは GLFW のキーコード（key が -1 のときだけスキャンコード）、マウスのボタンは GLFW の番号（左 0、右 1、中 2、4 は 3、5 は 4）で照合する
- マウスのコールバックは (button, action, mods) だけを使い、`pressed = action == 1`（REPEAT を渡すと解放とみなす）。`glfwGetMouseButton` は使わない
- 本物の状態を読むのは `glfwGetKey` だけ：setAll（マウスを掴み直すとき。`CURSOR_DISABLED` にする前なので、カーソルを掴んでいるかに依らず答える必要がある）、Ctrl・Shift・Alt、キーのイベントごとのクラッシュのキー、1.16 は F3 も
- 画面の中のクリックの修飾キー：1.16.1 はクリックのときに `glfwGetKey(340)`・`glfwGetKey(344)` で Shift を読む（`AbstractContainerScreen.mouseClicked`）ので、表の偽装に従い、置き換えた Shift でも Shift+クリックになる。1.21.11（1.21.9 以降）はマウスのコールバックの mods を使うので、物理のまま（26.3 は上の `SDL_GetModState()` で、これも物理のまま。README の制限）
- GLFW はコールバックを呼ぶ**前**に自身の `keys[]` を更新する。フォーカスを失うと、先にフォーカスのコールバックを呼び、その後で押しているキー（key ≥ 0）とマウスのボタンの RELEASE（mods 0）を送る
- key -1 のキー（JIS 配列の かな・ろ・変換・無変換・¥。1.21 の options.txt では `scancode.<N>`）は状態を持たない。リピートも PRESS で届き、フォーカスを失っても RELEASE は来ない
- IME が処理したキー（`VK_PROCESSKEY`）は届かない。PrintScreen は離したときに押下と解放がまとめて届く。Windows ではマウスのボタン 6〜8 は来ない

**SDL3**
- フォーカスを失うと、FOCUS_LOST の後に、押しているキーの KEY_UP を送る（windowID は正しい）。マウスのボタンは離さない（`SDL_ResetMouse` は `#if 0`）
- スモークテスト（LWJGL 3.4.3）では、最小化したときに KEY_UP が FOCUS_LOST より先に来た。どちらの順でも正しく扱えることを確かめた

**共通**
- キーボードのリピート（GLFW の REPEAT、SDL の repeat）でも `click` が増える（Q の長押しで続けて捨てる）。マウスのボタンはリピートしない
- ナレーターの切り替え（Ctrl+B）は、デバッグのキーより先に、キーのイベントの修飾キーで判定する。届けるキーのイベントの修飾キーは、すべて置き換えに合わせる必要がある（合わせないと、左 Ctrl → F3 の置き換えで F3+B を押したとき、物理の Ctrl のビットが残ってナレーターも切り替わる）
- キーの名前：1.21 と 26.x で、同じ名前が別のキーを指すものが 3 つある（`keypad.decimal`、`menu`、`world.2`）。26.x ではテンキーの「.」が `keypad.period`、アプリケーションキーが `application`、ISO 配列の追加のキーが `world.1`。名前のないキーは、26.x は `key.keyboard.<スキャンコード>`、1.21 は `key.keyboard.<キーコード>` と `scancode.<N>`。マウスは `key.mouse.2` が 1.21 では右、26.x では中

### 設計

**キーの表し方（`core/src/keybinds.rs`、`keytable.rs`）**
- `InputId`：キー（SDL のスキャンコード 4..512）かマウスのボタン（SDL の番号 1..=5）。どちらのライブラリにも依らない。GLFW との変換は `input_from_glfw_key`（key -1 は Win32 のスキャンコードで JIS のキー）、`glfw_key_of`、`input_from_glfw_button`、`glfw_button_of`。SDL のキーコードは `sdl_keycode_of`（US 配列の値）
- `keytable.rs` は、26.3 と 1.21.11 の jar から抜き出したキーの表（TSV）から生成した（生成のスクリプトはリポジトリの外）。2 つの表の突き合わせはテストで確かめる。JIS のキーの Win32 のスキャンコードの表（0x70・0x73・0x79・0x7B・0x7D）は手で書いた
- 名前の読み方は `Naming`：`Modern`（26.x の名前。settings.json と 26.x の options.txt）と `Glfw`（1.21 の名前と `scancode.<N>`。GLFW の版の options.txt）。数字の名前もゲームと同じく読む
- ラベルは `input_label` 1 つ（`A`、`F3`、`左 Ctrl`、`スペース`、`↑`、US 配列の記号、`テンキー 1`、`テンキーの Enter`、JIS だけのキーは `ろ`・`¥`・`変換`・`無変換`・`カタカナ/ひらがな`、`左クリック`・`ホイールクリック`・`マウスのボタン4`、名前のないキーは `キー 130` のようにスキャンコード）
- F3+C が使う `glfw_key`・`sdl_scancode`・`sdl_keycode`・`key_label` は、これまでどおり文字・数字・F キー・テンキーの数字だけ（全キーに広げると、実機で確かめていない F3+C の挙動が変わる）。デバッグの修飾キーと受け身のコピーのキーは `input_by_name` で引く
- `bindings_by_key`：options.txt の各キーに割り当てた操作（メニューの行の括弧）。ファイルの順で、`key.debug.*` は修飾キーとオーバーレイの切り替えだけ残す（ほかは F3 と一緒のときだけ動くので）。`mapping_label` にデバッグ修飾キー・オーバーレイの切り替え・GUIの切り替えなどを足した（ゲームの ja_jp の名前）

**設定（`core/src/settings.rs`、`render/src/rebinds_ui.rs` の `resolve`）**
- settings.json の `rebinds_enabled`（既定 true。`"true"`・`"false"` の文字列も読む）と `rebinds`（`{"from": 名前, "to": 名前}` の配列。26.x の名前だけ）。値の形が違えば、その項目だけ警告を出して既定値にするか捨てる（ファイル全体は退避しない）
- 捨てた値や項目があれば、`Settings::load` が元のファイルを `settings.rebinds-<unix>.json` に写し（`waypoint.rs` の `copy_path`。`backup_path` の `settings.corrupt-<unix>.json` と同じ形）、警告をログに出す。写した先は `#[serde(skip)]` の `rebinds_kept_in` に入れ、メニューの欄に「settings.json の置き換えに読めない項目があったので {ファイル名} に残した」と出す。
  手で書いた項目が、次にメニューで設定を変えたときの保存で消えるため（読めない項目を保存のときに書き戻すことはしない）。捨てたかどうかは、`load` の間だけ使う `thread_local` のフラグで知る。同じ中身の写しがすでにあれば、それを使い直す（起動やオーバーレイの作り直しのたびに写しが増えないように）
- `resolve` が使えないルールを除き、1 つずつログに出す（`rebinds: left out a -> b: <理由>`）：読めない名前、元にできないキー（Esc、Windows キー、PrintScreen、international1〜5、lang1〜5）、送れないキー（Esc、Windows キー）、ライブラリが扱えないキー（下）、同じキー同士、元のキーの重複（先のものを使う）、修飾キーなしのホットキーと同じ元のキー、33 個目以降。全体がオフなら何も使わない（`rebinds: off (N in the settings)`）。メニューの行の注記は、同じ判定（`check_rules`）から作る
- `resolve` はルールかホットキーが変わったときだけ呼ぶ（ズームのスライダーを動かす間は毎フレーム設定が変わるので、毎回呼ぶとログがあふれる）
- ライブラリが扱えないキー：`frame.rs` の `unsupported_inputs` が、ルールに出てくる id のうち、元のキーとして報告されない（`WindowSystem::can_receive`）か、ゲームに送れない（`can_send`）ものの一覧を作り、`resolve`・`check_rules` の第 3 引数に渡す。
  GLFW の `can_receive` は、GLFW のコードに変換して戻したときに同じ id になるもの（`world.2` を 26.x の名前で読んだ SDL 50 などは、GLFW が報告しない）、`can_send` は GLFW のコードがあるもの（1.21 の名前のまま書いた `menu`・`keypad.decimal`・`lang1` は、26.x の名前では SDL 118・220・144 で、GLFW にない）。SDL3 はどちらも、SDL3 が知るスキャンコードとボタン 1〜5。
  ログの理由は `the game's window library has no <名前>`、行の注記は「{キー} はこの版のゲームでは使えない」。メニューには、開いている間だけ `FrameInput::unsupported_inputs` で渡す
- `rebinds: N active (...)` は、`frame.rs` の `log_active_rebinds` が `set_rebinds` の後に、router が実際に使う一覧（`router.rebinds()`。キーの状態の偽装がないときに除くキーボードのキーを元にするルールも除いた後）で出す

**状態機械（`render/src/rebind.rs`、`Rebinder`）**
- 押したときに決め、その押下のリピートと解放は、押したときの決定に従う（その後でルールや画面が変わっても）。Toolscreen の置き換えの修正の多くは、解放のときに今のルールで決め直して、キーが押されたまま残ったことだった
- 置き換えるのは「ゲーム中」の押下だけ：オーバーレイが有効、ゲームがカーソルを捕まえている、メニューを閉じている、キーの割り当て待ちでない。チャットや画面に置き換えを入れないので、Toolscreen のような文字の層は要らない
- 元のキーごとの記録：`Passthrough`（そのまま渡した）、`Rebound(出力)`、`Orphaned`（フォーカスを失ったときに出力だけ離した。元のキーの解放はこれから来る）。ゲームに届けた id ごとに、押さえている数を数える（物理の W と X → W が重なっても、押下と解放は 1 回ずつ）
- リピート：`Rebound` は、そのときゲーム中で出力がキーなら出力のリピート、そうでなければ捨てる（キー → マウスのリピートは、ゲームが解放とみなすので捨てる）。`Orphaned` は捨てる。`Passthrough` と記録のないキーは今までの判定のまま
- 記録のある元のキーにリピートでない押下が来たら：GLFW の key -1 の `Rebound` はリピートとみなす。そのほかは解放を取り逃したとみなし、古い記録を捨てて判定し直す
- 記録のない解放（メニューを開いている間など、router が取った押下の解放）は、ルールがその id を押さえている間（`rule_holds`）は捨てる。ルール自身の解放で離す。
  渡すと、CapsLock → 左 Ctrl を押したまま Ctrl+I を 2 回押したとき、メニューに取られた物理の左 Ctrl の解放がゲームに届き、CapsLock がまだ押さえている左 Ctrl が離れる（その後は表の偽装とキーのイベントが食い違う）
- ルールが 0 個で記録もなければ、何もしない（今までと同じ動き）
- フォーカスを失ったとき（`focus_lost`）：押さえが 0 になる出力の解放を返す。元のキーの解放がこれから来るなら `Orphaned`、来ない（GLFW の key -1、SDL3 のマウスのボタン）なら記録を消す。`Passthrough` は残す（本物の解放がそのまま届く。消すと、W を押したまま Alt+Tab したときに歩き続ける）。ただし、離すイベントが来ない入力の `Passthrough` が、その id を最後まで押さえていれば、その解放も返す
- `RebindState`：押さえている (元, 出力) と、ゲームに離して見せる元のキー（`Orphaned` を含む）。両方に入る id（A と B を入れ替えて両方押している）は、押さえている方が勝つ。
  ほかに `passthrough`：ルールの出力になっている id の `Passthrough` の記録（安全網が見る。下）
- `forget_passthrough(id)`：`Passthrough` の記録と押さえを、ゲームに何も送らずに消す（安全網から）。消した id がデバッグの修飾キーで、ほかのルールが押さえていなければ、router の `debug_held` も外す

**入力の振り分け（`render/src/input.rs`）**
- `key()`・`button()` は `raw`（ゲームの知るキー）を受け取り、`Delivery`（`Forward`／`Consume`／`Send(出力)`）を返す。`Route` に変種を足すと、呼び出し側の `!= Consume` が黙って Forward にしてしまうので、型を変えて全箇所を直させた
- 順序：記録のある元のキーは、まず rebinder が決める。そのほかは今までの判定（割り当て待ち、メニューのキー、メニュー、ホットキー、ズーム）を物理のキーで行い、ゲームに渡す押下だけを rebinder に渡す
- ホットキーとメニューは物理のキーと物理の修飾キーで判定する（左 Ctrl → F3 にしても Ctrl+I でメニューが開く）。デバッグの修飾キーを押しているか（`debug_held`）は、ゲームに届けたキーで決める（マウスのボタン4 → F3 を押している間は Z・J・K をゲームに渡す。F3 をほかのキーに置き換えていれば、物理の F3 では渡さない）
- 置き換えて送ったキーの押下とリピートの後と、置き換え中の元のキーのリピートを捨てた後は、次の文字（WM_CHAR、TEXT_INPUT）を 1 回捨てる（X → T で開いたチャットに x が入らない）
- 「追加」の割り当て待ち（`start_input_capture`）：次の押下を `Captured::Input(id)` で返す。キーボードは修飾キーを含むすべて、マウスはホイールクリックとボタン 4・5（左右のクリックはメニューの操作に使う）。Esc で取り消し
- 割り当て待ち（「追加」とホットキーの両方）で取ったキーやボタンは `capture_held`（最大 4 つ）に覚え、そのリピートと次の解放も捨てる（`capture_release`）。リピートも捨てるのは、取ったキーを押したままメニューを閉じたとき、リピートだけがゲームに届いて押したままになるのを防ぐため。押下は取ったのに解放をゲームに渡すと、F3 を置き換え先にしたとき、メニューの裏で F3 画面が切り替わる（ゲームは F3 の解放だけで切り替える）。
  同じキーがもう一度押されたら（自動リピートは除く）、解放は来なかったとみなして忘れる。`set_enabled(false)` でも忘れる。Esc の取り消しでは覚えない
- `set_rebinds(rules, keyboard_sources)`：`keyboard_sources` が false なら、元がキーのルールを除く（下のキーの状態の偽装ができないとき）

**ゲームから見えるキーの状態（`hook-win/src/rebind_state.rs`）**
- 置き換えを押したまま画面を開閉すると、setAll が本物の状態を読み直し、元のキーの操作が押され、置き換え先が離される。Ctrl+Q の Ctrl やクラッシュのキーも本物の状態で読まれる。そこで、ゲームが読むキーの状態を置き換えに合わせる
- SDL のスキャンコードごとの 512 個の `AtomicU8`（本物／押している／離している）。ロックを使わない（ゲームは GUI のアイテムを描くたびに Shift を読むなど、頻繁に読む）。router のロックを持つ者だけが書く
- プラットフォームは、ゲームにイベントを渡す直前（GLFW が自身の `keys[]` をコールバックの前に更新するのに合わせる）、フォーカスを失ったとき、安全網の後に、router の `RebindState` から書き直す。ゲームのコードは、router のロックを外してから呼ぶ
- 読むのは `glfwGetKey`・`SDL_GetKeyboardState` のデトア、キーのイベントの修飾キーのビット、F3+C の確認。マウスのボタンは入れない（ゲームが読まない）
- `glfwGetKey`・`SDL_GetKeyboardState` のデトアが入っていなければ、キーボードのキーを元にするルールを使わない（警告 `rebinds: the game's key state reads are not hooked; keys are not rebound` と、メニューの注記）

**GLFW（`glfw_input.rs`）**
- キーとマウスのボタンのラッパーで router に渡し、`Send` なら出力を、ゲームのキーかマウスのボタンのコールバックで送る。キーのスキャンコードは `glfwGetKeyScancode`、key -1 は表の値（key -1 に `glfwGetKeyScancode` を呼ぶと、GLFW_INVALID_ENUM がゲームのエラーコールバックに行く）。マウスのボタンにリピートは送らない
- 修飾キーのビット：置き換えが修飾キーに関わっている間は、キーのイベントの Shift・Control・Alt・Super のビットを、GLFW 自身の `keys[]` と表から作り直す（CapsLock と NumLock のビットは残す）。クリックの mods は物理のまま（キーに置き換えたクリックにも、物理の mods を付ける）
- `glfwGetKey`：F3+C の修飾キーの偽装（1.16 向け）が最優先、次に表、なければ本物。`real_get_key` は偽装しない
- フォーカス：ゲームのフォーカスのコールバックの前に、`focus_lost` の解放を修飾キー 0 で送る（GLFW 自身の解放と同じ）。その後に GLFW が送る元のキーの解放は、router が捨てる

**SDL3（`sdl_input.rs`）**
- `SDL_PollEvent` のフィルタで、router の決定に従い、呼び出し元のイベント（128 バイト）をその場で書き換える。windowID と timestamp は残す
  - キー → キー：scancode と key（`sdl_keycode_of`）。down・repeat はそのまま
  - キー → マウス：type 0x401/0x402、button、down、clicks 1、which 0、残りは 0
  - マウス → キー：type 0x300/0x301、scancode、key、down、repeat 0。mod は本物の `SDL_GetModState()` に置き換えを反映したもの（関数を引いて呼ぶだけで、フックしない）
  - マウス → マウス：button
- 修飾キーのビット：イベント自身の `mod` の、置き換えに関わるキーのビットだけを立てる・消す（SDL の配列は、今渡しているイベントより先の状態になっていることがあるので、配列からは作らない）
- `SDL_GetKeyboardState`：表に強制がある間は、SDL の配列を static のバッファに写して書き換えたものを返す（ゲームは読むたびに関数を呼ぶので、今の状態が見える）。SDL の配列が 512 より長いときは書き換えない
- FOCUS_LOST：`focus_lost` の解放を、router のロックを外してから、注入のキュー（`INJECTED`）の先頭に積む
- `SDL_GetModState` はフックしない（効くのはクリックの修飾キーと Alt+F4 だけ）。クリックの修飾キーは物理のまま

**安全網（`rebind_state::lost_releases`）**
- 解放が来ないことがある：IME に取られた（半角/全角など）、フォーカスを失っている間に離した、26.x がワールドの読み込み中などに入力のイベントを捨てた（下）、そのほか。JIS の IME のキー（international1〜5、lang1〜5）は、解放が来ないことがあるので、そもそも元のキーにできない。GLFW で key -1 になるキーのうち `InputId` になるのは `JIS_KEYS` のかな・ろ・変換・無変換・¥ だけで、どれもこの中にある（ほかの key -1 は `InputId` にならず、置き換えの対象にならない）ので、安全網が key -1 の元のキーを離すことはない
- スワップの後に毎フレーム、2 種類の id を `GetAsyncKeyState` で調べる
  - 押さえている元のキー（`RebindState::held` の元）。100 ms 以上（2 フレーム以上の確認で）離れて見えたら `release_source` で離す（GLFW はスワップの後にコールバックで、SDL3 は `INJECTED` で）。ログは debug の `rebinds: <元> is up, but its release never came; releasing <先>`
  - ルールの出力になっている id の `Passthrough`（`RebindState::passthrough`）。同じく 100 ms 離れて見えたら `forget_passthrough` で、ゲームに何も送らずに忘れる。ログは debug の `rebinds: <id> is up, but its release never came; forgetting its press`
- `Passthrough` を見るのは、26.3 がワールドに入るとき（`Minecraft.doWorldLoad` の待ちのループ）と「セーブしてタイトルへ戻る」（`Minecraft.disconnect`）の間に `RenderSystem.pumpEvents` を呼び、`SDL_FlushEvents(768, 4871)` でキーとマウスのイベントを捨てるため（26.3 の javap で確認）。
  「選択したワールドで遊ぶ」を押した左クリックの解放が捨てられると、左クリックの `Passthrough` と押さえ（1）が残り、H → 左クリック の H の押下は押さえが 2 になって捨てられ、ゲームにクリックが届かなかった（物理の左クリックを一度するまで直らない）。ゲームは画面が変わるときに自分の状態を離しているので、解放は送らない。
  GLFW にはこの捨て方はないが、同じ安全網が働く。`SDL_FlushEvents` をフックして捨てられる解放を拾う方法もあるが、安全網を広げるほうが小さい
- すぐに離さないのは、ゲームが最後にイベントを読んでからスワップまでに離したキーの、本物の解放より先に合成しないため（先に合成すると、後から来る本物の解放が元のキーのまま届く。F3 を元にしていれば F3 画面が切り替わる）
- VK は `MapVirtualKeyW(スキャンコード, MAPVK_VSC_TO_VK_EX)`。マウスは、左右のクリックが `VK_LBUTTON`・`VK_RBUTTON`（`GetAsyncKeyState` は物理のボタンを読むので、`GetSystemMetrics(SM_SWAPBUTTON)` で左右の入れ替えを見る。`button_virtual_key`）、中・4・5 が `VK_MBUTTON`・`VK_XBUTTON1`・`VK_XBUTTON2`。
  Pause は `VK_PAUSE`（GLFW 3.4 は Pause を 0x45 と報告し、Windows ではそれが NumLock のスキャンコード）、NumLock は `VK_NUMLOCK`、テンキーの数字と「.」は NumLock がオフのときのナビゲーションキーの VK も見る。Win32 のスキャンコードがないキーは調べない（押されているとみなす）
- 何も押さえていないフレームで router のロックを取らないよう、`apply` が `REBOUND`（ルールが出力を押さえている）と `PASSED`（`passthrough` がある）を書く。`apply` は早期 return のときも含めて、毎回 `WINDOW` と `PASSED` を書く

**F3+C**
- 送る前の「押していない」の確認は、ゲームから見える状態（表と本物）で行う。置き換えで修飾キー・コピー・クラッシュのキー（コピーのキーに捨てる操作があれば Ctrl も）を押さえていれば、`Failure::KeysHeld(Some((元, 先)))` で「マウスのボタン4（F3 に置き換え）を押している間は座標を取得できない」と出す
- 送る F3+C のイベントは置き換えを通らない（今までどおり）。利用者自身の F3+C は、ゲームに**届けた**コピーのキーの押下で窓を開く
- options.txt は 5 秒ごとに 1 回読み、デバッグのキーと `bindings_by_key` の両方に使う。名前はフックしたライブラリに合わせて読む（GLFW は `Naming::Glfw`、SDL3 は `Modern`）。割り当ての一覧は、メニューを開いている間だけオーバーレイに渡す

**メニュー（`render/src/rebinds_ui.rs`）**
- 「ウェイポイント」の後、「状態」の前の畳める欄「キーの置き換え（N 個）」。説明の 1 行、「キーの置き換えを使う」、行（`マウスのボタン4 → F3（オーバーレイの切り替え・デバッグ修飾キー）` と「削除」）、「追加」
- 元のキーは押した直後に確かめ、断るときは理由を出して待つのをやめる（「{キー} は置き換えるキーにできない」「{キー} はもう置き換えている」「{キー} は「{操作}」に使っているので置き換えられない」）。置き換え先が断るキー（「{キー} はゲームに送るキーにできない」）か元と同じ（「同じキーには置き換えられない」）なら、置き換え先を待ったままにする。
  断った理由の注記は、取り消し（Esc、「取り消し」、欄を畳む、メニューを閉じる。`RebindMenu::cancel` と `Captured::Cancelled`）で消す（残すと、何も待っていないのに警告が出たままになる）
- 置き換え先を「左クリック」などのボタンで選んだら、router の割り当て待ちを止める（止めないと、次の Ctrl+I の Ctrl が割り当て待ちに取られ、メニューを閉じられない）
- 行の下の警告：読めない名前、使えない理由、元のキーをホットキーやその修飾キーにも使っている（「{キー} は「{操作}」（{ホットキー}）にも使っている」「…の修飾キーにも使っている」）。ホットキーの割り当てでも、ルールの元のキーと同じトリガーなら断る（「{キー} は置き換えに使っている」）
- 「キーを元に戻す」（`UiState::reset_hotkeys`）も同じく断る：既定のトリガーがルールの元のキーになっている操作は今のキーのまま残し、「{キー} は置き換えに使っている」を出す。
  残したキーと重なる、ほかの操作の既定のキーも今のまま残す（例：ズームを J のまま残すと、ウェイポイントの記録を J に戻せない）。そうしないと、メニューの割り当てと router の割り当てが食い違う
- 「削除」は 1 回で消す（ウェイポイントの削除のような確認はしない。置き換えは作り直しやすい）
- メニューが長くなったので、メニューの窓に縦のスクロールを付けた。egui の `Window::vscroll(true)` は窓の高さが既定の 420 に固定されたので使わず、中に `ScrollArea::vertical()` を置き、`resize(move |r| r.min_height(room))` で画面の高さまで伸ばす（`room` は毎フレームの `ctx.content_rect().height()`。中身が短ければ `ScrollArea` が縮む）。
  最初は `default_height(100_000.0)` にしていたが、egui 0.36 の `Resize` は既定の大きさを最初に一度だけ画面に合わせ、その後は覚えた大きさを下げることしかしないので、小さな窓で開いた後に最大化しても、メニューが伸びなかった。
  854×480（倍率 1 と 1.5）と 1920×1080 での大きさと、同じ `Context` で 854×480 → 1920×1080 → 854×480 と変えたときの大きさをテストにした。入れ子のウェイポイントの一覧は、小さな画面では 64 pt まで縮む
- メニューの窓は畳めなくした（`.collapsible(false)`）。畳むと中身のコードが動かないので、追加やホットキーの割り当て待ちが見えないまま続き、メニューを閉じようと押した Ctrl+I の Ctrl が置き換え先として追加されてしまう

**入れなかったもの**
- 置き換えの切り替えのホットキー（チャットと画面では最初から効かず、全体のチェックで足りる）、ルールごとのチェックボックス、キーを無効にするだけのルール

- 続く確認：LWJGL 3.3.3（既定と `--f3c-events`）、3.2.2（`--legacy`）、3.4.3（SDL3）の 4 通りで、ルール 7 個を入れて次を送った（`--f3c-events` では、画面を開いている間の確認だけ未実施）
  - マウスのボタン4 → F3 のまま C：F3+C で座標を取れる（`F3+C: location captured (manual)`）
  - CapsLock → 左 Ctrl を押したまま画面を開閉：A のイベントに Ctrl が付き（GLFW は mods 2、SDL3 は 0x2040 = CapsLock＋左 Ctrl）、`SETALL` で左 Ctrl は押され、CapsLock は離れて見える。離した後の A には付かない

  - マウスのボタン5 → Q を 0.6 秒押す：Q の押下と解放だけで、リピートは出ない
  - W を押したまま X → W：押下と解放は 1 組だけで、解放は W を離したとき。逆の順も同じ
  - 押したままフォーカスを失う（Alt+Tab ではなく、自前の囮のウィンドウを `SetForegroundWindow` で前面に）：出力が離れ、元のキーの解放は届かない。戻った後の X も正常。最後の `SETALL` はすべて 0
  - 押したままメニューを開く：メニューを開いている間のリピートは届かず、閉じた後に解放が届く

  - 安全網（PostMessage で押下だけを送る）：キーとマウスのボタン4 で、0.1〜0.2 秒で置き換え先を離す（`rebinds: key.keyboard.x is up, but its release never came; releasing key.keyboard.w`）。後から送った解放は、元のキーのまま届く。SDL3 はキーだけ（下の「確かめていないこと」）
  - 画面を開いている間は、元のキーとマウスのボタンがそのまま届く。X → W を押したまま画面を開き、画面の中で離すと、W の解放が届く
- そのとき分かったこと
  - フォーカスを失った後のマウスのボタンの解放は、前面でないウィンドウにも届き、元のボタンの解放としてゲームに渡る（エージェントがなくても、GLFW・SDL3 で同じ。害はない）

## 追記：インストーラー（2026-10-05）

`installer/`。Fabric のインストーラーのように、jar をダブルクリックすると DLL を置き、ランチャーのインスタンスの JVM 引数に `-agentpath:<DLL>` を足す（外すこともできる）。
Kotlin（利用者が学びたい）、Swing＋FlatLaf、Gradle。Java 8 以降で動く 1 つの jar にする（ダブルクリックで開く Java は、java.com の Java 8 のことも、Adoptium の 25 のこともある）。

### 見た目のライブラリ

最初は WebLaF で作ったが、Maven Central の最新版 1.2.14（2023 年）は Java 21・25 で初期化に失敗した（final のフィールドを書き換える `FieldHelper` が、Java 12 向けの実装のまま `UnsupportedOperationException`）。
Java 18 以降向けの修正は 2024-07 に master に入ったが、リリースされていない。Java 17 以下では動いたが、WebLaF は GPLv3 でもあり、利用者の判断で FlatLaf にした。FlatLaf は Java 8〜25 で表示できた。

### ランチャーの設定ファイル（ソースで確認）

- **公式ランチャー**：`.minecraft/launcher_profiles.json`（Microsoft Store・Xbox アプリ版は `launcher_profiles_microsoft_store.json`。Fabric のインストーラーと同じ名前）の `profiles.<id>.javaArgs`。
  `javaArgs` がない起動構成は、ランチャーの既定の引数（`-Xmx2G -XX:+UnlockExperimentalVMOptions -XX:+UseG1GC -XX:G1NewSizePercent=20 -XX:G1ReservePercent=20 -XX:MaxGCPauseMillis=50 -XX:G1HeapRegionSize=32M`）で起動するので、それに足して書く。
  この既定の文字列は記憶によるもので、この PC には公式ランチャーがなく確かめていない。起動中かどうかは、ランチャーは名前付きミューテックス `MojangLauncher` を持つ（Fabric はネイティブのライブラリで見る）が、Java からは見られないので、`tasklist` で `MinecraftLauncher.exe`・`Minecraft.exe` を探す
- **MultiMC**：インスタンスの `instance.cfg` の `JvmArgs`。`OverrideJava` か `OverrideJavaArgs` が true のときだけ使われ、そうでなければ `multimc.cfg` の `JvmArgs`（`MinecraftInstance.cpp` の `OrSetting`）。
  書式は `key=value` の行だけで、値は `\\`・`\n`・`\t`・`\#` でエスケープする（`INIFile::escape`）。インスタンスのフォルダは `multimc.cfg` の `InstanceDir`（既定 `instances`）
- **Prism Launcher**：同じく `instance.cfg` だが、`OverrideJavaArgs` だけを見る。`ConfigVersion` のあるファイルは Qt の INI（`QSettings`。`[General]` の節、`; , =` を含む値は引用符で囲む、`\\` などの C の書き方のエスケープ）で読み書きし、ないファイルは MultiMC の書式で読む（`INIFile.cpp`）。
  利用者の `instance.cfg` は CRLF で、`JvmArgs="-agentpath:C:\\reminedog\\reminedog.dll=log=debug"` のように書かれていた
- **MCSR Launcher**（`MCSRLauncher/Launcher`、Kotlin）：データは `launcher/`（`MCSRLauncher.jar` の隣。インストール先の既定は `%LOCALAPPDATA%\MCSRLauncher`）。インスタンスは `launcher/instances/<id>/instance.json`。
  `options.useLauncherJavaOption`（既定 true）が true なら、Java・メモリー・JVM 引数をまとめてランチャーの `options.json` から取る。JVM 引数は空白と改行で分けるだけで、引用符を解釈しない（`InstanceProcess.kt`）。
  起動中は `launcher/_app.lock` をロックしている。`instance.json` は kotlinx.serialization の `ignoreUnknownKeys`・既定値は書かない設定で、保存は `instance.bak.json` を経由する

### 設計

- 引数は文字列のまま編集する：reminedog の引数（ファイル名が `reminedog` で始まり `.dll` で終わる `-agentpath:`。引用符で囲まれていても見つける）だけを置き換え・削除し、ほかの部分（空白、引用符、順序）は残す。すでにあれば最初の 1 つのパスだけを置き換えてオプション（`=log=debug` など）を残し、2 つ目以降は消す
- DLL のパスは、空白・日本語などの ASCII 以外・`=`・引用符を含むものと、ドライブから始まらないものを断る（MCSR Launcher は引用符を解釈しない、Java の起動プログラムはコマンドラインを ANSI のコードページで読む、JVM は `=` でパスを切る）。既定の置き場所は `C:\reminedog`
- インスタンスがランチャー全体の設定を使っているとき：Prism・MultiMC は `OverrideJavaArgs=true` にしてランチャー全体の引数＋reminedog を書く。MCSR はランチャーの `javaPath`・`minMemory`・`maxMemory` を写して `useLauncherJavaOption=false` にし、ランチャーの引数＋reminedog を書く（今と同じ Java とメモリーで起動させるため）。外すときは、インスタンスの引数から消すだけで、切り替えは戻さない。ランチャー全体の引数に reminedog があるときは、インスタンスからは外せないと伝える
- 設定ファイルは行単位（INI）か、キーの順序と数値の書き方を保つ自前の JSON で書き戻す（インデント・改行コード・最後の改行もファイルに合わせる）。書き込みは一時ファイルからの置き換え。依存ライブラリを増やさないため、JSON と INI は自前
- 起動中のランチャーは設定をメモリーに持っていて後で書き戻す（Prism は起動のたびに `instance.cfg` を書く、MCSR は遊んだ時間を `instance.json` に書く）ので、選んだインスタンスのランチャーが起動していたら確認を出す
- ダウンロード：GitHub API の `repos/bafv4/reminedog/releases/latest` の `reminedog.dll` という名前のファイル。サイズ、`digest`（SHA-256。GitHub が付けるもの）、先頭の `MZ` を確かめてから置き換える。同じファイルがあればダウンロードしない。ゲームが DLL を読み込んでいると置き換えられないので、そう伝える。失敗したらインスタンスは変えない

### 導入済みの DLL を最新版にする（2026-10-06）

「最新版に更新」：チェックしたインスタンスが読み込んでいる DLL（JVM 引数の reminedog の `-agentpath:` のパス）を、その場所のまま最新のリリースに置き換える。JVM 引数もランチャーの設定も変えない。

- 置き換える DLL は、パス（大文字小文字と `/`・`\` の違いは同じと見る）ごとに 1 つにまとめ、どのインスタンスが読み込んでいるかを添えて確認を出してから置き換える。何個あってもダウンロードは 1 回（`Download.replaceAll`）。
  GitHub がハッシュを付けていれば、すべてのファイルが同じならダウンロードもしない。ハッシュがなければ、ダウンロードしてから比べる
- 置き換えは DLL の隣の一時ファイルからの移動で行う。ゲームが読み込んでいる DLL は移動に失敗し、そのファイルだけ失敗としてログに出す（ほかは置き換える）
- ドライブから始まらないパス（相対パスなど）は、ゲームの作業フォルダによって指すファイルが変わるので置き換えない。ランチャー全体の JVM 引数から読み込んでいる DLL も置き換える（ファイルを替えるだけなので）
- ランチャーの設定を書き換えないので、起動中のランチャーの確認は出さない
- 確かめたこと：単体テスト（3 つのうち 1 つが古い・1 つが同じ・1 つがない → ダウンロード 1 回で 2 つを置き換える、すべて同じならダウンロードしない、ハッシュがなければダウンロードして比べる、書き込めない場所は 1 つだけ失敗）。
  画面の操作（設定ファイルの写しで）：確認の一覧のまとめ方、reminedog のないインスタンスとドライブから始まらないパスを飛ばすこと、ダウンロードの失敗（リリースがない）で何も変えないこと
- 確かめていないこと：本物のリリースからの置き換え（リリースがない）。ゲームが読み込んでいる DLL で失敗すること（読み込んだ DLL はテストでは作れない）

## 追記：Sodium と高精細のズーム（2026-10-06）

利用者の 1.21.11（2026-10-05 から Fabric＋Sodium 0.8.15・Iris 1.10.8・Lithium）で、高精細のズーム中の画面がおかしくなった（バニラの 1.21.11 では問題なかった）。

### 原因

- Sodium の `features.render.viewport.GlStateManagerMixin` は、`GlStateManager._viewport` の中の `GL11.glViewport` を `@WrapWithCondition` で包み、直前の呼び出しと同じ値なら呼ばない（`skipRedundantViewport`。直前の値は static に覚えるだけ）
- 高精細のズームは、そのフレームでゲームが縦長の高さの `glViewport` を呼んだか（`TALL_VIEWPORT_SEEN` を毎フレーム戻していた）で、縦長で描いたかを判定していた。ズーム中の viewport はずっと縦長なので、Sodium が呼び出しを省き、ほとんどのフレームが「縦長で描かれていない」と判定された
- 判定に外れたフレームでは、ウィンドウに縦長の絵を写さず、引き伸ばす表示にしていた。ゲームの絵はこちらのフレームバッファに描かれていてウィンドウには届いていないので、ウィンドウに残った古い絵（または黒）を引き伸ばしていた
- Minecraft はライトマップを 1 ティックに 1 回 16×16 の viewport で描くので、そのフレームだけは縦長の `glViewport` が呼ばれて判定が当たる（1 秒に 20 回ほど）。その都度、失敗の回数が数え直しになるので、「縦長で描かない」として引き伸ばすズームに切り替える警告（3 フレーム以上かつ 1 秒以上）も出なかった。利用者のログも、ズームを始めた行だけで警告がなかった
- Iris は、シェーダーパックが選ばれていないので無効だった（「Shaders are disabled because no valid shaderpack is selected」）。Iris の `MixinGlCommandEncoder`・`MixinRenderTarget` も見たが、シェーダーを使うときの描画先の差し替えで、ウィンドウ（フレームバッファ 0）には触れていない

### 直したこと（`hook-win/src/tall.rs`）

- 縦長の viewport を見たことは、ズームを始めてから終わるまで覚えておく（GL の viewport は呼ばれなくても縦長のまま残っているため）。描き始める前のフレームや、まったく縦長で描かないゲーム（以前の 26.3）は、今までどおり判定に外れる
- 判定に外れたフレームで、ゲームの出力がこちらのフレームバッファに来ていたら、その元の大きさの部分（下から窓の高さ分）をウィンドウに写してから引き伸ばす。ズームの始めのフレームや、引き伸ばしに切り替わるまでの 1 秒に、黒や古い絵が出なくなる
- テスト用のプログラムに `--sodium`（`--mc` と一緒に）を足した。直前と同じ値の `glViewport` を省き、13 フレームに 1 回 16×16 の viewport を挟む（`SmokeImage.viewport`）

### 確かめたこと（2026-10-06、Windows、スモークに Z を `PostMessage` で 3 秒押させた）

- 直す前の DLL：GLFW（LWJGL 3.3.3）で、ズーム中の約 180 フレームのうち 176 フレームが判定に外れた（`output redirected: true, tall viewport: false, glViewport calls: 0, viewport now 854x1920`）。ウィンドウは黒く、警告は出ない。SDL3（3.4.3）でも 173 フレーム
- 直した後の DLL：`--sodium` あり・なしの GLFW、`--sodium` ありの SDL3 で、判定に外れたフレームは 0、ウィンドウは正しく拡大された
- 縦長で描かない版のスモーク（メインの描画先の大きさを変えない）：どちらの DLL も 1 秒後に引き伸ばすズームに切り替わる。その 1 秒の間、直す前は黒い画面、直した後は元の絵を引き伸ばした画面
- CI と同じ条件のスモーク（入力なし、`--mc` と `--mc --sodium`、GLFW と SDL3）は SMOKE OK でマーカーもそろい、警告なし。cargo test（core 159、hook-win 49、render 129）、clippy の警告なし
- 実機（利用者、Sodium 入りの 1.21.11、フルスクリーン 2560×1440）：ちらつかずに拡大できた。`=log=debug` のログでは、約 4 秒のズーム（2560×5760）の間に判定に外れたフレームは 0、警告なし

### 確かめていないこと

- 26.3 での見た目（ズームの判定の変え方は GLFW と共通で、SDL3 のスモークでは確かめた）
- Sodium のほかの描画の変更とズームの組み合わせ（今回の原因は viewport の省略だけで説明がつき、スモークで再現・修正を確かめた）

## 追記：ゲーム内ブラウザ（2026-10-07）

記事や動画を見ながら遊べるように、ゲームの画面の上にウェブページを小さく表示する（ピクチャインピクチャ）。
メニューを開いている間だけ、窓を動かし、大きさを変え、ページをマウスとキーボードで操作できる。閉じている間は表示だけで、ゲーム中に PageUp／PageDown でスクロール、↓ で再生／一時停止、←／→ で 10 秒戻す／進める（利用者が決めた既定。表示／非表示のキーは既定なし、非表示にすると動画を一時停止する）。

### 方式

**WebView2（Microsoft Edge）を画面に出さずに描かせ、その絵をテクスチャにしてオーバーレイに貼る。**

- `CreateCoreWebView2CompositionController`（visual hosting）で作り、`RootVisualTarget` に Windows.UI.Composition の `ContainerVisual` を渡す。その visual を `GraphicsCaptureItem::CreateFromVisual` と `Direct3D11CaptureFramePool` で取り込み（[pabloko の gist](https://gist.github.com/pabloko/5b5bfb71ac52d20dfad714c666a0c428) と同じ）、D3D11 のステージングテクスチャから CPU のバッファに写す。
  ゲームのスレッドは、新しい絵があればスワップのときに自前の GL コンテキストで `glTexSubImage2D`（BGRA）し、egui の `register_native_texture` で描く。egui_glow 0.36.2 は自前のテクスチャも sRGB ではない `RGBA8` として扱うので、色はそのまま合う
- 採らなかった案：
  - 別のウィンドウを重ねる：全画面では重ねられず（上の「採用しなかった案」）、フォーカスも奪う
  - CEF：配布が 200 MB 前後になり、標準のビルドは H.264／AAC を再生できない（ニコニコ動画など）。WebView2 は Windows 11 に入っていて、コーデックもある
  - CDP の `Page.startScreencast`・`CapturePreview`：JPEG／PNG を経由するので動画には重い
  - GL と D3D の共有（`WGL_NV_DX_interop2`）：CPU を経由しないが、スレッドとドライバーの条件が増える。重ければ後で替える
- **ページへの入力は CDP（`CallDevToolsProtocolMethod` の `Input.dispatchMouseEvent`・`Input.dispatchKeyEvent`・`Input.insertText`）で送る。**
  visual hosting の `SendMouseInput` は、WebView2 の内部のウィンドウが OS のフォーカスを取るという報告がある（全画面のゲームは最小化される）。CDP なら OS のフォーカスに触れない。`Emulation.setFocusEmulationEnabled` でページにはフォーカスがあると思わせる（キャレットやフォーカスの見た目のため）
- 座標：`BoundsMode` を生の画素、`RasterizationScale` をオーバーレイの倍率（`content_scale × scale=`）にするので、拡大率 100 % では CSS の 1 px が egui の 1 point。ページの拡大率は `ZoomFactor`。
  CDP のマウスの座標はページの CSS ピクセル（拡大率をかけた後）なので、egui の座標を拡大率で割って送る（テストで確かめた：拡大率 1.5 でも、送った座標がそのまま `clientX/Y` になる）
- キーは Windows のメッセージと同じ順に送る：`Event::Key` を `rawKeyDown`／`keyUp`、続く `Event::Text` を 1 文字なら `char`、それ以上（IME の確定）なら `insertText`。
  Enter は文字（`\r`）で動くが、ルーターは制御文字を文字として渡さないので、Enter だけ `keyDown` に `text: "\r"` を付ける。Ctrl+C／V はページが OS のクリップボードを使う。Esc はルーターがメニューを閉じるのに使うので、ページには届かない
- **ゲーム中の PageUp／PageDown は、ページの中央でホイールを 1 画面ぶん（高さの 7/8。Chromium のページ送りと同じ）回す。**
  CDP の PageDown キーは、ページを一度クリックするまで効かない（どのフレームにもフォーカスがない。`document.hasFocus()` は true でも）。`window.focus()` を流すと効くようになるが、ホストのウィンドウを前に出そうとするおそれがある（確かめていない）ので使わない。ホイールはフォーカスがなくても効く
- 動画は `ExecuteScript` で操作する：再生中の `video`／`audio`、なければ表示されている（大きさのある）一番大きいもの。Wikipedia などは見えない再生器を置いているので、大きさのないものは選ばない。
  非表示にするときは再生中のものをすべて止めて覚え（`window.__reminedogPaused`）、表示し直すときに再開する。自動再生の制限は `--autoplay-policy=no-user-gesture-required` で外す（ホットキーはページから見るとユーザーの操作ではない）
- **ゲームの前に別のウィンドウを出さない**：右クリックメニュー・開発者ツール・ステータスバー・既定のダイアログ・ブラウザのショートカット・パスワードと自動入力・ピンチとスワイプを無効にし、`window.print` は文書の作成時に空の関数にする。
  `NewWindowRequested` は Handled にして同じビューで開く。`LaunchingExternalUriScheme`（`mailto:` など）・ダウンロード（通知を出す）・権限の要求・Basic 認証は取り消す。ダイアログは alert と「ページを離れますか」だけ Accept し、ほかは取り消し（confirm は false）。ホストオブジェクトと Web メッセージも無効
- ユーザーデータ（クッキー、ログイン）は `%LOCALAPPDATA%\reminedog\WebView2`（なければ `<ゲームフォルダ>/reminedog/WebView2`）。すべてのインスタンスで共有する。同じ引数の WebView2 なら、2 つのゲームから同時に使ってもブラウザのプロセスを共有する
- 親のウィンドウ：visual hosting は `HWND_MESSAGE` を受け付けないので、表示しない WS_POPUP（WS_EX_TOOLWINDOW・WS_EX_NOACTIVATE）を作る。隠れたウィンドウだと Chromium が描画を止めるのではと心配したが、`--disable-features=CalculateNativeWinOcclusion` を付けて、テストでは絵が届いた
- URL はログに出さない（クエリにトークンが入りうる）。`=log=debug` でホスト名だけ

### 構成

- `core/src/browser.rs`：`PageInput`（マウス・ホイール・キー・文字）と CDP の JSON、アドレス欄の文字の URL への変換（スキームがなければ `https://`、ローカルは `http://`、ドメインでない言葉は Google の検索。`1.21` のような数字は検索）、動画の JS と通知の文言
- `render/src/browser.rs`：`BrowserView`（hook から）／`BrowserCommand`（hook へ）。メニューを開いているときの `egui::Window`（タイトル、⏴⏵⟳、アドレス欄、ページ、右下のつまみ）と、閉じているときの `Order::Background` の絵、メニューの欄、egui のキー → Windows の仮想キーと DOM の `code`／`key` の表。
  - 位置と大きさは settings の `browser_rect`（ページの部分、point）。窓は `auto_sized` で、ページの大きさは自分で決める（右下のつまみ）。窓が現れたとき（メニューを開いたとき、メニューを開いたまま表示したとき）は、ページが `browser_rect` に来るように窓を置く（窓の角からページまでのずれは描いてから測るので、合うまで最大 3 フレーム置き直す）
  - egui 0.36 の窓は、タイトルバーでドラッグする設定だと、`current_pos` より覚えている位置を優先する（`pivot_pos_before_begin`）ので、`WindowDrag::Anywhere` にしている（ページとつまみは自分のドラッグを取るので、動かせるのはタイトルと上の欄の空いたところ）
  - ページの大きさ（画素・倍率・拡大率）は、変わったときに 0.1 秒に 1 回まで `Layout` で送る
- `render/src/input.rs`：`BrowserAction` と専用のキュー（`take_browser_actions`）。表示切替は「ゲーム中」だけ、ほかは「ゲーム中かつブラウザを表示中」（`set_browser_shown`）だけ取る。F3 の規則はほかのホットキーと同じ。スクロールと秒送りはリピートでも繰り返す
- `render/src/overlay.rs`：ブラウザのキーは割り当てなし（`Option<Hotkey>`、settings では空文字列）を持てる。重なりの判定は割り当てのあるものだけで、照合の順は「現在地を更新」の後、ズームの前。メニューの「キー」の表は今までの 4 つ、ブラウザの 6 つは「ブラウザ」の欄の表（「外す」付き）。「キーを元に戻す」はそれぞれの表の分だけ戻す
- `hook-win/src/browser.rs`：ゲームのスレッドから使う部分。`CONTROL`（世代、メールボックス、表示中か、ページの大きさ）・`SHARED`（状態、URL、タイトル、通知）・`FRAME`（最新の絵）。どれも末端のロック。
  表示で起動し（世代を 1 つ進める）、終了でメールボックスを捨てる。古い世代のスレッドは `SHARED`／`FRAME` に書かない。`frame.rs` は `FRAME` を `try_lock` して、取れたフレームだけ絵を上げる（ブラウザのスレッドが書いている最中なら前の絵のまま）
- `hook-win/src/browser/thread.rs`：STA、`CreateDispatcherQueueController`、親のウィンドウ、`GetMessageW` のループ。`WM_APP+1` でメールボックスのコマンド、`WM_APP+2` で取り込んだ絵を処理する。WebView2 を作る間（`wait_with_pump` がメッセージを回す）に来たコマンドは、作り終えてから実行する
- `hook-win/src/browser/webview.rs`：WebView2 の作成、設定、イベント、コマンド。`hook-win/src/browser/capture.rs`：D3D11 と取り込み。大きさが変わったら取り込みを作り直す。`SetMinUpdateInterval` で 60 fps まで（Windows 11 24H2 より前は効かない）

### GNU のビルド

ブラウザのスレッドは Direct3D 11・WinRT・COM（`d3d11`、`CoreMessaging`、`combase`、`api-ms-win-core-winrt-l1-1-0`、`ole32`、`oleaut32`）を読み込み時に import する（windows クレートは raw-dylib）。
Wine にそろっているか分からず、1 つでも欠けると DLL が読み込めず、JVM が起動をやめる。そのため GNU のビルド（Wine 用）では `thread`・`webview`・`capture` を外し、表示すると「この DLL（GNU でビルドしたもの）ではブラウザを使えません」と出す。
また webview2-com-sys は GNU では `WebView2Loader.dll` を import する（MSVC では `WebView2LoaderStatic.lib` を静的にリンクする。この lib は CRT を指定していないので `+crt-static` と両立する）。
MSVC のリリースビルドの依存は `dumpbin /dependents` で確かめた（vcruntime などはない）。
これらは読み込み時に解決されるので、`CreateDispatcherQueueController` のない古い Windows 10（1709 より前と思われる。確かめていない）では DLL ごと読み込めなくなる。遅延読み込み（`/DELAYLOAD`）にすれば避けられるが、失敗すると例外になるので今はしていない

### 確かめたこと（2026-10-07、Windows）

- WebView2 を実際に動かすテスト（`cargo test -p reminedog-hook-win browser -- --ignored --test-threads=1`。3 件、3 回とも通る）：
  赤いページの絵が届く、クリックの座標（拡大率 1.0・1.5、倍率 2.0 で `innerWidth` も）、入力欄への文字（1 文字ずつと IME の文字列）、クリックした後の PageDown のキー、`target=_blank` のリンクが同じビューで開く、非表示の間は絵が来ず表示し直すと来る、
  クリックしていないページで PageDown のキーは効かず、ホイールのスクロールは効く（7/8 ページ）、音声の再生／一時停止・秒送り・非表示での一時停止と再開・通知の文言、見えない video を選ばない
- 手元のスモーク（GLFW、854×480、表示スケール 125 %、`PostMessage` でキーとマウス。ナビゲーションのキーには拡張キーの印が要る）：

  ページの検索ボタンのクリック・文字の入力（候補が出る）・Enter で検索。その間ずっと `GetForegroundWindow` はゲームのウィンドウのまま
- render の単体テスト：既定の位置、画面に収める、ページの大きさを送る間隔、メニューの開閉で位置がずれない、メニューを開いたまま表示しても既定の位置に出る、クリック・ホイール・キー・文字の変換（CSS ピクセル）、アドレス欄の Enter。ルーターとキーの割り当てのテスト
